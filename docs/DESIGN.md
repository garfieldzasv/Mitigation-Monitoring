## 0. 结论速查

**整体可行。** 产品分成两个窗口：打本时看的**实时监控窗口**（宽约 475px），和打本后用的**复盘窗口**（独立窗口，尺寸不限，数据尽量详细）。两个窗口共用一套解析引擎。复盘窗口存的是原始日志行，打开时重新计算，以后加泳道图之类的分析，对旧记录同样有效（3.2）。

## 1. 背景与目标

在 ACT + OverlayPlugin 环境下，**逐条记录小队每名成员受到的每一次伤害**：打本时在悬浮窗里实时看，打完后在复盘窗口里细看。用途是复盘：谁在什么时候吃了什么伤害，当时开了哪些减伤和盾，为什么死；以后再看减伤和盾的释放时机是否合理。

参考的隔壁项目：

| 项目                | 技术栈                              | 借鉴什么                                                                                                                                                                            |
| ------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Skills Monitoring   | Vue 3 + Vite + TS，单文件 IIFE 产物 | 数据形态相同（逐事件 LogLine）。OverlayPlugin 桥接、日志行解析、职业表、技能数据（含冷却）、数据导入脚本、图标复制脚本、设置持久化、独立窗口的打开与位置记忆，都可以直接复用（9.2） |
| Horizoverlay Reborn | React 16 + CRA                      | 只消费 CombatData 汇总数据，形态不同。借鉴`localStorage` 容错包装和模拟数据的做法                                                                                                 |
| act analysis        | Node 脚本                           | 真机网络日志样本（1.4G）、伤害值解码算法（已与游戏战斗文本逐条核对）。第 2 节的实测都基于这批样本                                                                                   |

### 1.1 两个窗口

|      | 实时监控窗口                                     | 复盘窗口                                                                     |
| ---- | ------------------------------------------------ | ---------------------------------------------------------------------------- |
| 用途 | 打本时扫一眼：谁吃了多少伤害、减伤够不够、谁死了 | 打完后细看，后续扩展各种分析                                                 |
| 形态 | OverlayPlugin 悬浮窗（MiniParse 类型）           | 从监控窗口用`window.open` 打开的独立窗口；也能在普通浏览器里打开导入的文件 |
| 尺寸 | 宽 ≤ 500px，按**475px** 设计              | 不限，按 1280px 以上设计                                                     |
| 内容 | 当前（或上一）场的受击行和死亡行，7 列           | 所有保存的场次；全列明细、死亡回放、AOE 对比、统计，以后加泳道图             |
| 数据 | 引擎增量计算，只保留当前场次                     | 读存档（原始日志行），打开时用同一套引擎重算                                 |

### 1.2 已确认的需求（2026-10-03）

1. 自动攻击照常显示，伤害名称就是日志里的“攻击”
2. 0 伤害行显示（大多是盾全吸收，见 2.1）
3. DoT 行显示，用单独的背景色
4. 死亡复盘在单独的复盘窗口里完整显示
5. 两种状态：打本时的实时监控、打本后的记录复盘。复盘窗口的数据尽量详细；以后可能加泳道图，查看减伤 / 盾技能的释放时机
6. 监控窗口宽度控制在 500px 以内，约 475px 最好；复盘窗口不限
7. ~~防护职业的被动特性减伤算进倍率~~（已改为不计入，见第 20 条）
8. 显示全团还是 8 人，由 ACT 的配置决定，悬浮窗不提供切换
9. 默认保留 20 场，另加收藏的场次
10. 暂不支持导入 ACT 网络日志文件，但留好接口（2026-10-08 起已支持，9.5）
11. 监控窗口高度 300~400px，可以调整；表格布局，高度只影响显示的行数
12. 发布沿用 GitHub Pages + Release zip
13. 时间只显示 `mm:ss`，不要小数
14. 职业用职业图标，不用文字
15. 倍率改为显示减伤率：×0.72 显示为 28%；颜色按数值渐变，0% 红色，50% 绿色
16. 监控窗口第三列的列名改为“来源”，列的内容（技能名）和过滤方式不变
17. 监控窗口不显示连接方式，左侧不留空白
18. 监控窗口新记录在最上方，滚动条保持在顶部；往下滚动时出现“返回顶部”
19. 游戏数据里没有名字的普通攻击（日志里是 `unknown_xxxx`）显示为“攻击”
20. 防护职业被动特性的 20% 不计入减伤率
21. 易伤、增伤不计入减伤率（数值未知），也不再让减伤率带 `?`
22. 对这次伤害不生效的减伤（伤害类型不符、同组不叠加）在状态列里照常显示，用黑白图标表示不参与计算
23. 监控窗口“来源”列固定宽度，状态列自动占满剩余宽度，能放几个图标按列宽计算
24. 未减伤估算按每个人实测的承伤系数折算到其他队员的水平（坦克约 ÷0.63），同一招各人可以直接比较；减伤率仍不计防护职业被动（2026-10-06）。2026-10-07 改为不折算（参考 souma 减伤记录；系数出自样本，其他工具都不做这种折算），见 5.5
25. 复盘窗口放一个“计算说明”图标，悬停说明各项数据是怎么来的、误差多少。读者是看复盘的人，不讲计算逻辑，不写公式、引言和括号说明（2026-10-06）

### 1.3 非目标

- 不读游戏内存，ACT 日志拿不到的数据一律不做
- 不做未减伤原始伤害的“真值”（游戏不下发，只能估算，见 5.5）
- 不做 DPS / 治疗排行（ACT 和 Horizoverlay 已经覆盖）。复盘里的治疗数据只用于还原受击和死亡的过程
- 不做 PvP
- **只做副本**（2026-10-07 确认）：主要目标是 8 人讨伐（讨伐歼灭战、大型任务、绝境战），兼顾 4 人迷宫和 24 人大型任务。不做野外和特殊场景（新月岛、优雷卡、天佑女王、深层迷宫、挖宝地图等）的记录和复盘。按游戏数据判断：区域（TerritoryType）对应的副本（ContentFinderCondition）的内容类型（ContentType）是 2 迷宫挑战、4 讨伐歼灭战、5 大型任务、28 绝境战。哪些区域的战斗存档由设置“不存档的区域”决定（2026-10-08，树状复选，6.2），默认只存副本（迷宫挑战、讨伐歼灭战、大型任务、绝境战、诛灭战、特殊迷宫探索）

## 3. 总体架构

### 3.1 分层

```
┌────────────────────────────────────────────────────────────────────┐
│ UI 层（Vue）                                                         │
│   MonitorPage（悬浮窗，475px）       ReviewPage（独立窗口）            │
│     MonitorGrid / DeathRow             EncounterList / DamageTable    │
│     HeaderFilter                       DeathReplay / AoeCompare / ... │
├────────────────────────────────────────────────────────────────────┤
│ 应用层（composables）                                                 │
│   useOverlayBridge  useLiveEngine  useArchive  useReviewModel        │
├────────────────────────────────────────────────────────────────────┤
│ 核心层 core/（纯 TS，不依赖 Vue，可单测）                               │
│   overlay/  logline/  combatants/  party/  status/  mitigation/      │
│   engine/   archive/  filter/  game/  settings/                      │
├────────────────────────────────────────────────────────────────────┤
│ 存储层：IndexedDB（场次存档） + BroadcastChannel（跨窗口通知）          │
└────────────────────────────────────────────────────────────────────┘
```

### 3.2 存原始日志行，复盘时重算

监控窗口在内存里算受击行，同时把相关的原始日志行写进场次存档。复盘窗口读存档，把原始行重新喂给同一个引擎（`core/archive/replay.ts` 的 `replayArchive(meta, lines)`），得到全部明细。

这样做的原因：

1. **复盘要的数据比监控多得多**：治疗、状态起止、Boss 读条、HP 和护盾曲线，以后还有泳道图。存原始行，以后新增的分析对旧记录同样有效，不需要做数据迁移
2. **结果一致**：监控和复盘跑的是同一个引擎、同样一行一行地算，复盘显示的就是监控当时显示的（见下）
3. **修正能回溯**：减伤数值表更新或算法修正后，旧记录重新打开就是新结果
4. **能吃 ACT 日志文件**：OverlayPlugin 推送的 `LogLine` 和 ACT 网络日志文件是同一种格式，复盘窗口可以直接导入 `Network_*.log`，离线复盘任何一场（2026-10-08 起，9.5）

代价是存储：每场 0.5~1.3 MB（2.2）。重算很快：hunt 夹具 13,127 行在 Node 里约 25 ms（11.2）。

**复盘必须和监控一样**（2026-10-07 决定）：监控时日志一条一条到，任何判断只能用已经到达的行；要等后面的行才能定的（护盾吸收要等之后的护盾报告，没有结算行的受击要等 10 秒），先给暂定值，后面的行到了再改（`rowUpdate`）。复盘虽然一次拿得到整场，也按同样的顺序一行一行重算一遍，不用“未来”的行去改前面的结论（原先的护盾账本复盘时求解两遍，第二遍用第一遍对整场学到的数值；账本已去掉，5.6）。为此：
  - 监控引擎读的就是存档里的裁剪形式（`archivedForm`，6.2），存档不会少了监控用过的信息
  - 每一场只用这一场自己的行：从挂盾行确认过的盾量（给没有说明可依的技能用）每场开打时清空，监控不沿用前几场的
  - `tests/archive.test.ts`：三份夹具的复盘结果与监控逐行完全相同（含盾吸收、全吸收、未生效、死因）

### 3.3 跨窗口数据通道

复盘窗口是 `window.open` 打开的普通弹出窗口，**不假设它能拿到 OverlayPlugin 的 API**（Skills Monitoring 的设置窗口也是让悬浮窗代为调用 TTS）。所以监控窗口是唯一的数据写入方：

| 通道             | 用途                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IndexedDB        | 场次存档（6.2）。开打、每 10 秒、脱战、封存时各追加一块；页面关闭（`pagehide`）时再写一次。悬浮窗崩溃最多丢 10 秒                                               |
| BroadcastChannel | 监控窗口每写一次就广播存档 ID（`{type: "archive", id}`）。复盘窗口收到后刷新场次列表；如果正看着这一场，就重新读存档重算，最多 3 秒一次，所以打本时也能实时跟看 |

两个窗口同源，共享 IndexedDB（ACT 的 `file://` 下已实测，11.2）。原计划的 `postMessage` 备用通道没有做：实测 IndexedDB 在 `file://` 下可用，而 `file://` 下弹窗读不了 `window.opener`。IndexedDB 不存在时存档退回内存，复盘窗口就看不到历史场次。

ACT 内置浏览器和系统浏览器的存储是分开的（Skills Monitoring 的 FAQ 里有同样的现象），所以在系统浏览器里复盘要走“导出 / 导入”（M9）。

```

   │

```

### 4.3 `21/22` 行字段与 flags

字段下标（`line[0]` 是行号）：

| 下标  | 字段                      | 下标    | 字段                                         |
| ----- | ------------------------- | ------- | -------------------------------------------- |
| 2 / 3 | 来源 ID / 名字            | 24 / 25 | 目标受击前 HP / 最大 HP                      |

|       |                           | 47 / 48 | ownerId / owner 名字                         |

**flags**（8 位十六进制，`AABBCCDD` 中 `DD` 是最低字节）：

| 位置            | 含义                                                                                                                                                                                                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DD` 效果类型 | `01` 闪避、`03` 伤害、`04` 治疗、`05` 格挡、`06` 招架、`0E/0F` 附加状态；其余（`1B` 等）忽略                                                                                                                                                                             |
| `CC` 次字节   | 伤害：`20` 暴击、`40` 直击（由玩家伤害行推断，待用游戏战斗文本核对），低位 `01~07` 含义未明。治疗：flags 第三字节的 `20` 是暴击（LogGuide：`0x200004` 是暴击治疗；ACT 插件也按这一位读）。原先写的“没有可用的暴击位、给队友的治疗全部带 `0x200000`”是错的：1,048 次治疗里带这一位的 263 次在游戏战斗文本里都是暴击，不带的 783 次都不是（2026-10-07 核对）。复盘暂不显示治疗暴击；盾量用不到它（盾按日志里的治疗量算，暴击已在其中，5.6） |
| `BB` 伤害类型 | 低 4 位攻击类型：1 斩、2 刺、3 打、4 射（物理），5 魔法，6 特殊（暗）；高 4 位属性：1 火、2 冰、3 风、4 土、5 雷、6 水、7 无                                                                                                                                                           |

**数值解码**（与 `act analysis/heal-audit.js` 相同，已用游戏战斗文本核对）：`value` 按字节记作 `AA BB CC DD`，若 `CC & 0x40`（大数值标记），数值 = `DD AA BB`，否则数值 = `AA BB`。

**`value` 的 `CC` 是效果标记**：`0x40` 大数值（见上）、`0x80` 效果作用于**来源**。挂在攻击上的自我治疗（浴血、原初的血气、骑士连击的回复）都在目标是敌人的行里，带 `0x80`，治疗量归施放者；给队友的治疗没有一次带 `0x80`（1003 样本：自我治疗 226 次全带 `0x80`，给他人 460 次都不带，`core/logline/effect.ts` 的 `findHealEffects`）。

## 5. 核心算法

### 5.1 受击判定与来源归类

一条 `21/22` 行生成一条受击记录，需要同时满足：

1. 目标是玩家（ID 以 `10` 开头）。记录时不按小队过滤，显示时按显示范围过滤（5.2）
2. 8 组效果里有一组的类型是 `01 / 03 / 05 / 06`
3. 来源不是玩家（ID 不以 `10` 开头）。**不看来源的 owner**

为什么不看 owner：野外为某个玩家刷出的敌人（FATE、任务、7.x 的“护领…”怪）在 `03` 行和每条 `21` 行的下标 47 里都把这个玩家记成 owner。原先按“owner 是玩家 → 召唤物 → 不算受击”过滤，结果这些战斗里打在自己身上的伤害全被丢掉（0928 样本克扎玛乌卡湿地一场：日志里 125 次受击，记录 0 次，用户反馈“野外战斗有时没有数据”）。18 份样本日志里，所有打到玩家身上、owner 是玩家的 `4xxxxxxx` 来源共 31 种，全是敌人，没有一个是真正的宠物：PvE 里玩家的召唤物不会伤害玩家。

和 Horizoverlay Reborn 的对比：它只有 `CombatData`（名字、职业），用“名字是 `名字 (主人)` 且主人带职业”区分队伍的宠物和敌人。对它的问题（ACT 友方名单里哪些无职业单位该显示）这是合理的；但它的前提“敌人没有主人”在野外不成立（为你刷出的敌人会被命名为 `护领树林人 (YOU)`），只是这些敌人一般不在 ACT 的友方名单里，影响有限。我们有日志行和 ID，要回答的只是“这一下是不是打在玩家身上的伤害”，用不上 owner。判定集中在 `core/engine/damageRecorder.ts` 的 `isDamageTaken`，复盘的“敌方读条”也以它为准。

owner（`registry.ownerOf`：先取行内下标 47，没有就查 `03` 行；换区清空，`04` 行删除）现在只用来给治疗的施法者注上主人（小仙女、地星）。读条也不能按 owner 分敌我：陆行鸟搭档、亲信 NPC 也挂在玩家名下，所以“敌方读条”= 这场里伤害过玩家的单位（按名字）的读条（5.8）。

- 自动攻击照常记录，显示为“攻击”。很多 Boss 的普通攻击在游戏数据里没有名字，ACT 记成 `unknown_ae46` 这样（ACT 实测：永远之暗歼灭战里每 3 秒打一次坦克的 `unknown_ae46`）。判断依据是游戏数据 Action 表的 ActionCategory = 1（自动攻击）：全表 1,533 个，其中 852 个没有名字。这类技能名字为空、为 `unknown_*` 或日文“攻撃”时显示为“攻击”；有名字的（如“机关炮”）保留原名。“隐藏自动攻击”按这个类别判断，不看名字（`core/game/actions.ts`，数据见 9.4）。另外，cactbot 时间轴里作者标注为自动攻击的技能也算（`--auto--`、`Attack`、`# B25E --sync--: Autoattack` 这类标注，9.4）：新一些的 boss 常用游戏数据记成“能力”的无名技能当自动攻击（格莱杨拉波尔的 `unknown_b25e`），这类也显示为“攻击”。2026-10-07 起，原先“按用法认出无名自动攻击”（同一来源 8 次以上、间隔中位 1.5~10 秒、跨半场）的规则去掉，以 cactbot 的人工标注为准。没有名字但不是普通攻击的技能（部分机制）仍显示 `unknown_*`
- 0 伤害照常记录：碰到了盾的标“全吸收”（5.6），处于无敌状态标“无敌”。格挡、招架和全吸收不互斥：一下格挡的伤害也可以被盾全部吸收，判定两个都标（复盘“格挡·全吸收”，监控“格盾”；10-06 炼净之狱3 風紧扯呼的静电之月、半神神圣）
- 没有自己 `37` 行、护盾也看不出它打到的受击，判为“未生效”（5.6）：照常列出，判定写“未生效”，伤害灰显，不计入任何合计，HP 视为不变。它没有自己的 HP：受击前 HP 只能取锁定时的最后一次 HP 更新，同一时刻的另几下还没结算，常是满血（09-05 飞针的 `9F10` 显示 100%）。所以受伤明细的 HP 列写“—”，详情侧栏“死亡前最后几次受击”里整行灰显、HP 写“未生效”、减伤写“—”（2026-10-09，用户确认）。死亡回放显示的是之后 HP，它没有，那一格本来就空着，不改
- `24` 行（目标是玩家、类型为 DoT）生成一条 DoT 记录。两个窗口里 DoT 行都用单独的背景色
  - **是哪个减益在跳**（实机反馈：中量级2 的大量“持续伤害 / 未知”其实来自“中暑”）：`24` 行几乎从不写状态（敌方 DoT 99% 的 `effectId` 是 0），但跳伤时目标身上会持续掉血的敌方减益通常只有一种。按游戏数据认出这类减益（负面状态、说明写着“体力逐渐流失 / 持续受到伤害”等，378 个，9.4），目标身上只有一种（同名的几个算一种，两个“猛毒”）时，伤害名称就是它的名字（中暑、中毒、出血），来源是施加它的敌人。18 份日志里玩家受到的 3,266 跳中 94% 能这样认出，4% 有两种不同的减益、1% 一种都没有，这些仍显示“持续伤害”。`effectId` 非 0 时直接按它。实现：`damageRecorder.ts` 的 `tickedStatus`
  - 施加减益的若是场地本身（`26` 行的来源是 `E0000000`，没有名字，如护锁刃龙的“护龙威压”），名字认得出、来源仍是未知
  - `24` 行里的 HP 是跳伤**之前**的值（样本 410 次全部如此），直接作为受击前 HP
  - `24` 行的来源字段不可靠：hunt 夹具里写成受击者本人 305 次、写成其他玩家 244 次、写成敌人只有 17 次。来源是玩家时一律当作未知，只保留非玩家来源
  - 0 伤害的 DoT 大多发生在有盾时，和普通受击一样按护盾报告结算，在跳伤时生效（5.6）

### 5.2 显示范围

显示全团还是 8 人由 ACT 的配置决定，悬浮窗不提供切换。

ACT 的解析范围（Parse Filter）不影响日志行（2.1），但决定 ACT 战斗统计里有哪些人。所以以 OverlayPlugin 推送的 `CombatData` 为准：

- **范围** = 自己 + 自己小队（`PartyChanged` 中 `inParty` 为真的成员）+ `CombatData.Combatant` 里的名字。`Limit Break`、宠物、敌人的名字也在 `CombatData` 里，但它们不会是受击行的目标，不影响
- **自己和小队永远在范围内**：ACT 的任何解析范围都包含他们，所以在副本里不改变结果。`CombatData` 本身不能单独当范围用：它是 ACT 的友方名单（`GetAllies()`），ACT 从“谁对谁出手”出发、以自己为起点推出敌我，**自己还没出手时名单为空**，**开场动作少时会短暂认反成“自己 + 敌人”**（Horizoverlay Reborn 反编译 ACT 得出，见其 DEVLOG“开场几秒，名单变成「你 + 敌人」”）。原先只看 `CombatData`：名单为空时整场都不显示，认反的几秒里队友不显示。认反时混进来的敌人名字不会是受击行的目标，不影响。这条规则同样作用于旧存档（`compileScope` 用存档里保存的自己和小队 ID）
- **开打后第一份 `CombatData` 到达之前**（约 1 秒），只有自己和小队。范围外的玩家照样记录，只是先不显示，范围确认后补出来
- **一场之内范围只增不减**：开打时的小队，加上战斗中出现过的成员和 `CombatData` 名单。原因是实测里队伍会在战斗结束前后变化：hunt 夹具过本后 10 秒内有人离队；水晶塔那场任务完成，小队列表在脱战前 2 秒就变成 0 人。只减不增会让这些人的行消失
- **场次结束时冻结**：范围写进这一场（`Encounter.scope`），之后再显示这一场都按冻结的范围；复盘时按存档里的范围显示
- 死亡行、过滤器的成员列表、AOE 对比都只含范围内的玩家
- 单人时 `PartyChanged` 只有自己一人，`CombatData` 里也只有自己

### 5.3 战斗分段（场次）

2026-10-07 起按 cactbot oopsy 的做法（`core/engine/encounter.ts`）：

- **只认自己这边的战斗**（2026-10-08，实机反馈“进入野外地图就开始了监听”）：`260` 行有两个状态，LogGuide 说 `inACTCombat` “可能包含你周围的其他人，而不是你自己”，`inGameCombat` 是游戏认为你在战斗中。野外别人在打怪时 ACT 处于战斗状态、日志里也有别人和怪之间的伤害行，原先两者都会开一场，一进地图就开始记录。现在照 cactbot（oopsy、raidboss 都只看 `inGameCombat`）：ACT 的战斗状态不开场，别的玩家（不在自己小队里的，含 24 人本的其他小队）的伤害也不开场
- **开始**：`260` 行游戏说自己进入战斗，或自己 / 小队成员与敌人之间的第一下伤害，取先到的（oopsy 以第一条攻击行开始，Triggevent 以玩家第一次对敌人出手开始）；一场结束后 5 秒内不开新的一场（oopsy：团灭后迟到的行）。复盘重放存档时，从存档记的开打时刻那一行开场、不管那一行按现在的规则算不算开打（旧存档是按旧规则开的场），之前的行只用来恢复状态（监控当时记得“刚结束 5 秒内不开新场”，重放时没有这一状态）。原先“开打前 5 秒内的受击并入”和“团灭后要先看到一次双方脱战”两条（样本得出）去掉
- **结束**：`260` 行游戏说自己脱战（`isGameChanged` 为真、`inGameCombat` 为假），但自己倒地时不算：倒地的人的战斗状态说明不了小队还在不在打（`25` 行之后，到 HP 读数大于 0 或换区为止算倒地）；或 ACT 和游戏都脱战（自己一直没进战的小队战斗）；胜利或团灭（`33` 行，胜利行也立即结束这一场，同 Triggevent）、换区。`260` 行会比时间戳更晚的行后写出（ACT 插件晚写）：时间戳早于这一场开打时刻的 `260` 行说的是开打之前的状态，不结束这一场（水晶塔夹具：小队成员 13.856 秒出手开场，之后写出一条 13.800 秒的“游戏脱战”）。Triggevent 只按胜利 / 团灭 / 换区结束、不看脱战，但它的一场覆盖整个副本，多 Boss 的副本（迷宫、大型任务）会并成一场，不适合这里；`33` 行的 `40000001` 是整个副本开始的指令（进本时发，带的是副本时限，如 `E10` = 3600 秒），不能用来认出 Boss 战
- 有倒计时（`268` 行）时，可选以倒计时结束为 0 秒
- **结果**：团灭 / 过本 / 未知。按 LogGuide 对 `33` 行的定义：过本 `40000003`（多变 / 异闻迷宫的 `40000002`）；团灭 `40000005`（淡出）、`4000000F`（6.2 起的淡入）、`40000010`（6.2 以前）。场次是 `260` 行脱战结束的，而 `260` 也受 ACT 自己的战斗超时影响，可能比胜利 / 团灭行先到：结束后到下一场开始或换区之前到的胜利 / 团灭行仍决定这一场的结果（只改“未知”的；2026-10-07 起不再限 10 秒，那是没有出处的数）
- **迟到的死亡行**：场次结束后、下一场开始或换区之前的 `25` 行仍归入这一场；按 HP 归 0 的时刻归场：下一场已经开打、而这个人是在上一场里 HP 归 0 的，归上一场（连续拉怪的副本）。存档在结束后一直记到下一场开始或换区
- **战斗时间**：记录时间 − 开始时间，显示为 `mm:ss.s`；悬停显示本地时间
- 监控窗口只显示当前场次（脱战后继续显示上一场，直到下一场开打）；历史场次在复盘窗口里看

### 5.4 状态追踪 `StatusTracker`

- 对每个实体（队员和敌人）维护 `Map<statusId, {stacks, sourceId, appliedAt, expiresAt}>`，由 `26` 行写入、`30` 行删除
- **状态一直有效到它的 `30` 行**（2026-10-07 起，同 Triggevent、cactbot oopsy）：对敌人和自己小队的人，ACT 插件在实体的状态列表里看到它没了时写 `30` 行；另外单位移除（`04`）、团灭（`33`）、换区时清空。时长只用来显示剩余时间，过了时长还没有 `30` 行的显示 0。**小队以外的玩家**（24 人副本的其他小队）ACT 只偶尔看到他们的状态列表，`30` 行常常不来（样本里一场大型任务有 4,299 次过期很久的状态还挂着），所以按 souma 的做法：时长过后再留 3 秒就失效（cactbot oopsy 本来也只跟踪小队）。原先“过了时长再等 1 秒就当没了”（`EXPIRY_GRACE_MS`）去掉；时长超过 9,000 秒的按无限（Triggevent 的规则），原先的“0 秒也算常驻”去掉
- **常驻状态**：游戏数据标为常驻的（Status 表的 `IsPermanent`，即游戏里不显示倒计时的，1,499 个：防护职业姿态、舞伴、关心，以及光环和地面技能在效果期间持续补发的——诗人的歌、节制的全队减伤、站在野战治疗阵 / 庇护所里的减伤），一直有效到 `30` 行，剩余时间显示“常驻”。这些状态在日志里每 3 秒重发一次、带着几秒到 60 秒的时长（关心写 60 秒，歌写 5 秒），只看日志会显示一个不断回跳的倒计时（实机反馈：关心一直剩 57~60 秒、歌一直剩两秒左右）。持续时间 0 或 9999 秒的也按常驻：这一条没有出处，只作兜底
  - 2026-10-07 更正：国服数据仓库的 Status 表从第 17 列起列名错位，原先读的“IsPermanent”其实是 InflictedByActor，歌、节制等因此没被标出，于是另加了一条“同一来源隔 1.5~4.5 秒把 10 秒以内的状态补满就是光环”的规则（从样本得出，没有出处）。现在按国际服数据（xivapi/ffxiv-datamining，表结构跟着现行版本维护）的列定义读对这一列（两边数值 99.96% 一致），光环识别规则去掉
- 受击时拍快照：目标身上的全部状态、来源身上的全部状态。快照随记录保存，之后状态怎么变都不影响已有记录
- 同一状态来自两个施加者（两个坦克的雪仇）分开记录，哪个生效由倍率模型决定
- **挂状态那一行的修正字节**（5.5）：`21/22` 行的 `0E` / `0F` 效果带着这次挂上的状态的修正值，跟到随后的 `26` 行上（同 Triggevent 的“预挂”：按施放者、目标、状态配对，5 秒内，先后都行；施放者另认同名单位：Boss 的分身施放、本体名下的 `26` 也对得上）。同一次挂上的重发（盾吸收、层数变化、常驻状态的重发）沿用；没有技能行而重新挂满的，数值未知（可能是另一个技能挂的）
- **Boss 的分身**：Boss 的机制大多由同名的隐形分身释放，而雪仇等减益只挂在本体上。hunt 夹具里 8 个名为“护锁刃龙”的单位在造成伤害，只有一个挂着雪仇。所以来源快照会**并入同名单位身上的状态**，并标记为“继承”（`inherited`），界面上在悬停提示和详情侧栏里注明（原先用虚线色条，15px 宽的图标下虚线看起来像被截断，已改为实线）。只有分身借：玩家只能对可选中的敌人出手，被玩家的技能打到过的敌人是真实单位（同名的几只小怪之一），只用自己身上的；借也只从被玩家打到过的同名单位借。**日志验证结论：游戏确实把本体上的减益算到分身的伤害上**（继承的雪仇在魔法伤害上估计 10.0%，1,818 次，区间 8.4~11.5%；见 [mitigation-check.md](mitigation-check.md)），所以继承的减益参与减伤率计算。同名的小怪之间不再互相并入。出处（2026-10-07 查）：晓月时期的系统性说法（Meru 的减伤指南、Icy Veins《FFLogs Mitigation》）是 Boss 的普通分身吃本体的雪仇、昏乱、牵制，FFLogs 也把本体的减益复制给分身计算；不吃的是“自成一体”的单位（球、炮台、史莱姆、元素块、部分分身、不可选的骑士 / 蛮神），随副本不同。名字不同的这些我们本来就不借；名字相同而不吃的（个别分身）日志分不出来，会多算。7.x 没有找到系统性的出处
- **层数**：26 行的层数字段对不叠层的状态装的是别的数据（“告解”显示 65526 层），只有最大层数大于 1 的状态才记层数
- **重复施加、覆盖与刷新**（2026-10-05 用 18 份国服日志核对，用户的游戏观察全部吻合）：

  | 情况 | 游戏的表现 | 日志里的样子 | 样本 |
  | --- | --- | --- | ---: |
  | Boss 身上的减益（雪仇、昏乱、牵制、武装解除）被另一名队员再放 | 新的替换旧的，持续时间刷新 | 同一时刻先一条旧施放者的 `30`，再一条新施放者的 `26`（满时长） | 518 次，无一例外 |
  | 队员的盾被另一名队员施加同一种 | 替换 | 同上 | 100 |
  | 队员的盾被同一人再施加，新盾**更大** | 覆盖，持续时间刷新 | 施放行里状态效果是 `0x0E`，随后一条满时长的 `26` | — |
  | 同上，新盾**不比现有的大** | 不覆盖，持续时间不变 | 施放行里状态效果是 `0x14`（值的高 16 位是状态 ID），**没有 `26` 行** | 盾 591 次；均衡预后再施放 525 次里 209 次、鼓舞 353 次里 222 次 |
  | 盾被部分吸收等，状态还在 | 持续时间不变 | 游戏重发一条 `26`，时长是**剩余时间**，没有施放行 | 盾 169、减伤 146 |
  | Boss 增伤、减伤类 buff 同一人重复施加 | 刷新 | 满时长的 `26` | — |
  | 两人的同一状态并存 | 只见于告解（两个白魔的全大赦，24 人副本）和受伤加重（不同敌人各给一份） | 两条 `26`、没有 `30` | 17 / 4 |

  **处理**：状态追踪不模拟这些规则，完全照日志来，所以监控窗口和减伤率天然正确：替换靠 `30` 行删掉旧的；每条 `26` 都按它写的时长算到期（满时长就是刷新，剩余时间就是没变）；没覆盖时没有 `26`，状态保持原样。两人并存的同一状态在减伤率里只算一次。
  **复盘的死亡回放**（`ReplayDetail`）据此区分：`获得`（原来没有）、`刷新`（时长被延长超过 0.5 秒）、`层数`（只变了层数）、`未生效`（施放行有 `0x14`：已有同类效果没覆盖，显示现有的还剩几秒）、`失去`；只是重发、什么都没变的 `26` 不列出（原先一律标成“刷新”）
- 中途打开悬浮窗：队员状态用 `38` 行重新同步；敌人身上的减益持续时间都短（10~15 秒），自然补齐
- 复盘时另外输出**状态区间**（谁、什么状态、谁挂的、从几秒到几秒），给死亡回放和泳道图用

### 5.5 减伤倍率

游戏不下发未减伤的原始伤害，所以只能按“已知效果表”计算理论值。**减伤率只算减伤**：

```
倍率 = Π(1 − 减伤%)        减伤率 = 1 − 倍率
```

| 参与计算       | 来自     | 例子                                                                           |
| -------------- | -------- | ------------------------------------------------------------------------------ |
| 目标身上的减伤 | 目标快照 | 铁壁 20%、野战治疗阵、节制、坚角清汁                                           |
| 来源身上的减益 | 来源快照 | 雪仇 10%、武装解除 10%、昏乱（魔法 10% / 物理 5%）、牵制（物理 10% / 魔法 5%） |
| 副本机制的减伤 | 目标快照 + 挂上它的技能行 | 技能说明里没有数值的：挂状态那一行写的修正值                                   |
| 这一下被格挡 / 招架 | 技能行伤害效果里写的减免 | 格挡、招架各自的比例（日志给出）                                               |

不参与计算、但在状态列和明细里照常列出的：目标身上的易伤、来源身上的增伤（见下）。

规则（实现：`core/mitigation/multiplier.ts`）：

- **按伤害类型取值**：物理伤害（攻击类型 斩 / 突 / 打 / 射）取减伤表的物理数值，魔法取魔法数值。吐息（攻击类型 6，游戏数据 AttackType 表的 ブレス；此前误标为“暗”）和没有攻击类型的伤害（类型 0，多是全屏大招）按哪种防御结算，游戏数据里没有说明，只吃物理、魔法数值相同的减伤，分开取值的（昏乱这类）记为数值未知。不按样本给它们指定类型（此前按样本定成“吐息按魔法”，已撤回）。昏乱、牵制在 7.x 对另一种伤害也有 5%（国服说明原文“令目标物理攻击造成的伤害降低 5%，魔法攻击造成的伤害降低 10%”，日志回归也是 4.2% / 4.8%），照常计入
- **无敌和保底 1 血**（导入时按状态说明分类）：“均无效化”“一切攻击都无法造成伤害”“暂时无敌”是无敌，这一下伤害无效、不参与护盾结算；“无法令体力减少到1以下”“体力减为1”（死斗、行尸走肉、出死入生等）是保底 1 血，状态栏里同样显示为无敌类，但伤害照常结算、照常被盾吸收。原先两者不分，战士、暗骑开减伤时的受击都被当成没打到盾。此前手工补的两个无敌状态 ID 已删，由说明文字认出（同类的共 35 个）
- **作用范围按状态说明里“受到的伤害增减”那一小句**：写“物理”只对物理伤害，写“魔法”只对魔法，两者都写或都不写对所有伤害；写“火 / 冰 / 风 / 土 / 雷 / 水属性”的只对日志里同元素的伤害（`21/22` 伤害效果的属性），不知道这一下的属性时未知。说明里带日志判断不了的条件（接近 / 远离 / 距离 / 方向 / 特定攻击 / 光暗属性 / 极性 / 因子，或紧挨在前、以“…时”结尾的条件句）的，数值未知。只看那一小句，“受到物理攻击时会发动反击”这类别处的物理不算（`scripts/game-data/statusEffects.ts`）
- **取哪个字节**：只有一种增减效果的状态取 LogGuide 说的修正字节（右数第二字节）；还有别的增减效果（造成的伤害、治疗量、最大体力）的，只有它的符号唯一时取那个符号的字节（缩小：造成伤害降低、受到伤害增加，取正的那个），同号的分不清（攻击形态：造成伤害提高、受到伤害增加）记为数值未知。易伤按层乘（样本里的字节没有随层数成倍的值）；叠层的副本减伤数值未知（没有依据说明层怎么算）
- **说明里取决于日志查不到的参数的数值不用**：新月岛辅助职业技能“防护”按辅助职业等级 60% 或 90%（`PlayerParameter(108)`），日志里没有这个等级，所以不从说明定值，改由挂状态那一行的字节给出
- **对这次伤害不生效的减伤计为 0**：只减魔法伤害的（抗死、异想的幻光）遇到物理伤害、同组里被更强的盖过的（见下），明细里标“不生效”或“不叠加”，状态列里显示为黑白图标
- **易伤、增伤不计入减伤率**：减伤率只说明这一下开了多少减伤。它们在状态列里显示为红色，不影响减伤率，也不会让减伤率带 `?`
- **易伤的数值取自日志**：敌人的技能给玩家挂易伤时，那一行的状态效果里写着修正值（OverlayPlugin LogGuide 对 `0E` / `0F` 效果的定义：flags 右数第二字节，有符号，“You can examine these to find damage down and vulnerability percentages”）。同一个状态在不同副本、不同技能给的值不同，所以只认挂上它的那一行，**没有按状态 ID 的数值表**，没见过的副本一样能算。多层时每层一份，乘层数。作用范围按状态说明：写“物理”的只对物理伤害，写“魔法”的只对魔法，都没写的对所有伤害；吐息、无攻击类型遇到只限一种的，数值未知。明细里标“+30%，易伤不计入减伤”，未减伤估算里除掉。日志里找不到挂上它的那一行（开打前挂的）或字节符号不对时数值未知，明细里标“数值未知”，未减伤估算标 `≤`。此前按样本测定“受伤加重每层 +20%”写成固定表，已删除：那只是样本里多数技能给的值
- **Boss 增伤**数值未知，对同一次施放的所有人相同，不影响同一招各人的比较，不做处理
- **副本机制的减伤取自日志**：技能说明里没有数值的减伤类状态（副本给的受伤减轻、魔法受伤减轻等，数值只在服务器上），用挂上它的那一行的修正值（负数，−20 即减 20%），作用范围同上按状态说明。职业技能的减伤仍以技能说明为准、不读字节：字节含义因状态而异，有的状态不放修正值（告解的两个字节是随机数），两种效果的状态哪个字节是哪种也不统一
- **`?` 只表示有数值未知的减伤**：受击者身上有减伤类状态，技能说明和日志都给不出数值，这时实际减伤比显示的高
- **不叠加的同组状态只算最强的一个**：行吟 / 策动 / 防守之桑巴（说明原文“无法…共存”），异想的幻光 / 炽天的幻光。落选的在明细里标“不叠加”
- **按等级取值**：行吟 / 策动 / 防守之桑巴 98 级以上 15%、以下 10%。等级取受击者的（同一副本里大家同步到同一等级）。实测（按所用数值分组回归）：按 10% 算的 584 下魔法伤害实际减 11.0%（9.0%～13.0%），按 15% 算的 687 下实际减 14.0%（10.7%～17.2%）。旧版本的同类工具不分等级一律按 15%，同步到 90 级的副本（如 10-06 万魔殿 炼净之狱3）会比本项目多算约 4 个百分点（23% 对 27%）
- **按施放者取值**：骑士的坚守由骑士自己的圣盾阵给是 15%，由干预给别人是 10%（共用一个状态 ID）；干预本身 10%，骑士当时有铁壁 / 预警 / 极致防御时 20%
- **同一个状态来自两个人不叠加**（两个坦克的雪仇只算一次）；本体自己的优先于从同名单位继承来的
- **格挡、招架的减免取自日志**：技能行判定为格挡 / 招架的，伤害效果 flags 最左一字节就是这一下的减免（LogGuide：“For parries/blocks … this value indicates the reduction (treat it as an 8-bit signed integer), e.g. 0xEC => -20%”），明细里列为“格挡”“招架”。这一字节为 0 时数值未知（标 `?`）。此前按样本定的固定值（格挡 20%、招架 15%）已删除
- **盾不算倍率**：护盾类状态单独标记，吸收量单独成列（5.6）
- **防护职业被动特性不计入**（1.2 第 20 条）：它是坦克职业常驻的 20%，算进去会让坦克的减伤率永远比别人高 20%，看不出这一下开了什么。实测（同一次施放、都没有盾、已除去已知减伤）坦克吃到的是非坦克的 0.622 倍：20% 被动之外，坦克装备的防御还差约 22%。未减伤估算也不除掉它（见下）
- **DoT 跳伤不计算**，减伤率显示“—”：DoT 的减伤在挂上时已经结算，跳伤时身上的状态不说明问题
- **其余不在日志里的因素**不计入：装备防御力、等级差
- **未减伤估算**（复盘窗口）= (伤害 + 盾吸收) ÷ 倍率 ÷ 已知的易伤（2026-10-07 起同 souma 减伤记录的做法）：这一下打在这个人身上、没有减伤时的伤害。坦克被动和装备防御不算减伤，仍在其中，所以同一招坦克的估算比其他人低。有数值未知的易伤时数字前加 `≤`（实际更低，悬停写“含易伤”），有数值未知的减伤时加 `≥`。实现：`src/app/format.ts`
  - **易伤**：按日志字节除掉
  - 原先还除以每个人按场实测的“承伤系数”（职能典型值 + 本场同一次施放里和其他非坦克的比较），把各人折算到同一标准。系数的典型值和离散都是样本测的，没有出处，其他工具也都不做这种折算，已去掉

### 5.6 护盾吸收与受击后 HP

2026-10-07 起按“两事件”结算（`core/engine/shieldGroups.ts`），只用日志能确定的东西。原先的盾账本（按样本测出的结果行延迟分布、报告提前显示的比例、打穿后盾还在的 4.2%、各种估计的离散度、用别的受击推算这一下的伤害，最小二乘分摊）整个去掉；为它而设的补盾识别 200 毫秒、“提前 1 秒消失不算到期”、报告按 10 毫秒归并也一并去掉。

**一下受击是两件事**（参照 FFLogs 把输出拆成 calculateddamage / damage）：

- **计算**：`21/22` 行，技能“锁定”的时刻（LogGuide）。伤害和它碰到的盾在这一刻定下：快照时按身上全部减伤算出最终伤害，其中包括盾，快照之后才挂上的盾对这一下无效（Icy Veins，FFLogs Mitigation）
- **结算**：同序列号、同目标的 `37` 行，伤害真正作用到目标身上（LogGuide 引 Ravahn），带着结算后的 HP 和护盾。DoT 跳伤（`24` 行）计算和结算在同一刻

**日志里有什么**：

- 吸收量不在日志里。被盾挡掉的部分直接从伤害里扣掉，全吸收时伤害值就是 0
- **护盾报告**：`37` 行（完整形式）和 `38` 行带着这个人身上全部护盾的合计，单位是最大 HP 的整数百分比（LogGuide：取整到整数，方向没有说明）。`37` 的精简形式只有 HP，不算报告
- **同一时间戳 = 同一个服务器数据包**（Machina：包里每条消息都打上包头的时间戳）。ACT 插件写一条结算消息时先写 `37`，紧接着写它带的状态（`26`；状态栏位换了主人时先写旧的 `30`）；写状态列表消息时先写 `38`，再写变了的 `26/30`。所以紧跟在一条报告后面、同一个人、同一时间戳的 `26/30` 是那条报告的，报告的盾值已经算进了它们（泛输血被打破后补上的下一层）
- **计算和结算之间的报告不一定已经反映这一下**（有的已经显示，有的要到它自己的结算才显示）；它自己的结算一定已经反映
- **上盾那一行带着盾值的最低字节**（LogGuide）：能确认技能说明给出的大小时（`scripts/game-data/barriers.ts`：治疗量或最大 HP 的百分之几，按施放者的职业和等级取值），这层盾的大小精确到 HP

**分组**：同一个人的受击，只有“前面每一下都已结算之后、下一下之前”出现了一条带盾值的报告才分得开；分不开的几下是一组，只知道合计。

**打穿之后不再并入**（2026-10-08，实机反馈：战士原初的血气在野外群怪战斗里出现“攻击 ×28”）：一大群怪连续打一个人时，任何时刻都有已经计算、还没结算的受击，永远等不到“前面每一下都已结算”的报告，原先这一组会一直并下去，远远超过盾被打破的那一下。按上面同一条游戏规则（伤害只会打穿已经空了的盾）：组里有一下打穿了、且之后没有挂上新盾，那么之后的受击计算时身上没有盾，不属于这一组，也不开新组。这一组就在打穿的那一下结束：吸收量 = 组前的盾 + 打穿之前挂上的盾，不需要组后的报告；之后到挂上新盾为止，这个人身上没有盾（相当于一条 0 的报告），打穿前就在身上的盾随后消失（`30`）或被重新挂上时，剩余量是 0、不算“剩下多少不知道”。这一组的受击还没全部结算时出现的报告可能还没反映它们，不作为之后的依据（同“计算和结算之间的报告不一定已经反映这一下”）。夹具上：hunt 最大的组仍是 8 下（全被盾吸收、日志确实分不开），24 人本最大的组从 14 下降到 4 下（同一瞬间的多段伤害），参与成组的受击从 143 行降到 79 行

**一组的吸收量** = 组前最后一条报告的盾 − 组后第一条报告的盾 + 其间挂上的盾（两条报告各按当时的最大 HP 换算）：

- **其间挂上的盾**：挂盾行的最低字节能确认大小的，按那个大小计入；泛输血被打破后在同一条结算消息里补上的下一层，按第一层的大小计入（技能说明：“消耗 1 档泛血印重新为目标附加防护罩”）；第一层的大小不知道时，打穿的那一下之后的报告就是新的一层，由此得知。确认不了的，吸收量只知道**下限**（≥）
- **其间消失的盾**：被这一组的受击打破的不影响；到期的（`30` 行在“挂上时间 + 时长”之后：LogGuide 说 `26` 行的时长只会已经倒数了一点）或在受击之前就没了的，剩下多少不知道，吸收量只知道**上限**（≤）。在一条报告同一时刻消失、不是到期的（受击之后状态列表才补上的 `30`），那条报告已经算过
- 既有下限又有上限的，定不出（?）
- **组里最后一下打穿了**：游戏里伤害只会打穿已经空了的盾，所以到它为止身上的盾全被吃掉，吸收量 = 组前的盾 + 它之前挂上的盾；它之后挂上的不算
- 一个 `26` 行对应的状态已经在身上、而结束时间移动不到 2 秒的，是参数变化，不是新盾（ACT 插件对已有状态只在结束时间移动超过 2 秒或参数变化时才写 `26`）

只有一下的组，吸收量就是这一下的（`shieldAbsorbed`）；几下的组只有合计（`shieldGroup`）。

**没有自己 `37` 的受击**：等 10 秒（Triggevent）；它的目标或来源死亡、团灭、换区时立即判断。算生效（LogGuide：不是每个技能都有 `37` 行；souma、DeathRecap 也按受击行计入），除非 HP 更新（`37/38/39`，不会过时）显示伤害没有扣上：受击前最近一次 HP 更新之后到 10 秒内，没有治疗，而 HP 一次也没有降到“受击前 HP − 其他受击 − 这一下的伤害”（超过剩余 HP 的按归 0）。没生效的（`noEffect`）不计入任何合计，也不当作致命一击；表格里判定写“未生效”（监控窗口写“无效”）。
- **先扣除其他受击**（2026-10-08，用户确认）：“其他受击”是这次 HP 更新为止、自己的 `37` 行已经到了的那些受击（每条 `37` 行给的就是那一下扣完后的 HP）。它们已经把 HP 扣到 0 的，这一下就没有可扣的了：未生效。原先不扣除，别的受击把 HP 打下去也算到这一下头上。实例（09-05 狂热糖潮的飞针）：三根针同一时刻锁定在满血 175,438 的大海原身上，`9F12` 的 `37` 显示 57,957（= 175,438 − 117,481），`9F13` 的 `37` 显示 0，`9F10`（96,685）没有 `37`；同一根针在另外两个目标身上都有 `37`，只有他没有：轮到他时他已经被打到 0。原先这一下算作生效，计入合计，死亡回放里“最后 10 秒受击”多出 96,685
- **“其间有治疗”按行的先后算**：只算作为基准的那次 HP 更新**之后**的治疗，同一时刻排在它前面的已经包含在这次更新里（上例 37.396 那跳持续治疗排在同一时刻的 `38` 前面）；也只看到其他受击把 HP 扣光为止。原先按时间、含等号比较
- **受击前 HP 取上一次 HP 更新**（2026-10-08，用户确认）：有自己 `37` 的，取这个人在这条 `37` 之前的最后一次 HP 更新（`37/38/39`）；没有的，取锁定时最后一次 HP 更新；都没有时才用技能行里的目标 HP。技能行里的目标 HP 是锁定时从内存读的，可能是旧值，上例三行都写满血，致命的那一下实际是从 57,957 扣起的。溢出量随之按这个算（133,872 − 57,957 = 75,915）
  - **加减之后的跳**（同日，用户确认）：那次更新之后、这一下之前的 DoT / HoT 跳（`24` 行）按跳量加减：DoT 减（不低于 0）、HoT 加（不超过最大 HP）。LogGuide：只有 `37/38/39` 的 HP 是更新，其他行（含 `24`）的 HP 是从内存读的；`24` 的跳量是这一跳施加的量。所以 `24` 行里的 HP 不用，只用跳量。DoT 那一跳自己的受击前 HP 也这样算（原先用 `24` 行里的 HP）
  - **核对**（34 份样本，只统计，未据此改规则）：没有盾参与、有自己 `37` 的 42,648 下受击，“受击前 − 受击后 = 伤害”成立的：用技能行里的 HP 27,359 下（64.2%），用上一次 HP 更新 41,703 下（97.8%），再加减之后的跳 42,312 下（99.2%）。剩下 336 下：同一时刻另一条扣血的行排在这一下的 `37` 后面（行的先后不一定是因果先后），或同一包里有治疗、这一下之前人在 0 HP 后来被复活。同次核对：改判为未生效 180 下（共 5,568,946，抽查两例都是同一时刻多下、其他下的 `37` 已解释全部扣血），反方向 0 下；致命一击没有变化；溢出量变了 199 次死亡
- **同一时刻锁定的几下，按各自 `37` 行的先后**（2026-10-08，用户确认）：LogGuide：`21/22` 是动作锁定，`37` 是动作真正发生。同一个人同一时刻的几下，真正扣血的先后看它们的 `37` 行（上例先 `9F12` 后 `9F13`，和技能行的先后不同）。复盘窗口的受伤明细、死亡回放、详情侧栏的“死亡前最后几次受击”按这个顺序列，只在这几下之间换位，别的行不动（一次 AOE 的各行仍在一起），没有 `37` 的排在后面（`core/engine/types.ts` `inEffectOrder`）。监控窗口不重排：`37` 行约 0.2 秒后才到，那时再换位会挤动正在看的行（7.1），数值照样按上面两条算

**受击后 HP**：它自己的 `37` 行的 HP（多段伤害同一序列号的几行都填这一下之后的 HP）；没有 `37` 的不显示。

**全吸收**：伤害为 0、不是闪避、碰到了盾。格挡、招架的一下也可以全吸收，判定两个都标（5.1）。

**显示**（7.1、8.2）：每一下各占一行（1.2 第 2 条“每人每次受击一行”；2026-10-08 起不再把一组合成一行，原先的合并行在群怪战斗里会把十几二十下并成“攻击 ×28”），组里每一行的盾吸收写“共≈…”，悬停说明是和另外几下的合计；详情侧栏列出同组的每一下和合计（名字按出现次序计数，如“护龙威压 ×3 + 咆哮”，伤害相加，各下减伤不同时未减伤估算给范围）。盾吸收的写法：≈ 两条报告定出的值（各取整到整数百分比，误差约 1% 最大 HP），≥ / ≤ 只知道下限 / 上限，? 定不出，… 还有受击没有结算。

### 5.7 死亡归因

收到 `25` 行（死者是小队成员）时，每次死亡只按它自己的行判断（团灭是结果，不是死因），依次：

1. **即死**：技能行里带即死效果（`0x33`，LogGuide “Effect Types”）的，就是死因，显示“{名字}被「{技能}」即死”
2. **cactbot 的标注**：cactbot oopsy 的作者为各副本标注了“被某个技能击中（或获得某个状态）之后死亡 = 击退坠落 / 击退至墙 / 某机制”（`deathReason`，9.4）。20 秒内被标注的技能击中、之后没有再受到技能伤害就死亡的（oopsy 死亡报告的规则），击退坠落、滑落、击退至墙都是**地形杀**，显示“{名字}死亡（地形杀）”，不写技能、不写标注来源；其他机制（目前只有“没解死宣”）显示“{名字}死亡（没解死宣）”
3. **致命一击**：往前找，窗口 6 秒（搜索范围）。`37` 行的 HP 是更新值、不会过时（LogGuide），所以**结果行显示 HP 归 0 的那一下**就是致命一击；同一时刻几下都显示 0 的，取 `37` 行最先到的那一下（之后的打在已经归 0 的人身上；2026-10-08 起按 `37` 行的先后，原先按技能行的先后）。`25` 行有凶手时，没有显示 0 的，取最后一条生效的受击：没生效的不算，结果行已经到了的优先
4. **`25` 行没有凶手**（`E0000000`、名字为空）、也没有一下的 `37` 显示 HP 归 0：**地形杀**（souma 减伤记录的规则：凶手是 `E0000000` 即“地形杀”）。死前最后一下不算致命一击（10-06 万魔殿 炼净之狱3：白鳥翔满血吃了一下 21,067 的普通攻击，0.5 秒后从平台掉下去）
5. 找到致命一击：“{名字}（{职业}）受到源自「{来源}」的「{技能}」伤害而死亡了”，标出溢出量（伤害 − 受击前 HP，受击前 HP 见 5.6）；DoT：“…受到持续伤害而死亡了”
6. `25` 行有凶手、却没有伤害记录：“{名字}被「{凶手}」击倒，没有伤害记录”

2026-10-07 去掉的规则（出自样本、没有出处）：按坐标判坠落（死前 6 秒低了 5 码以上、坐标行晚到 0.5 秒）、按活着的人到过的范围判场边即死区、没有凶手时按 HP 更新判断“打得死”的一下、死亡回放里的“疑似读条”。这些情况现在由第 2、4 条覆盖：没有凶手就是地形杀。

### 5.8 复盘的派生数据（完整模式）

### 5.9 阶段（在场 / 离场）

2026-10-07 起按 xivanalysis 找“停手时间”的做法（`core/engine/phases.ts`）。cactbot 时间轴的阶段是逐个副本人工写的（文件头的 `-p` 是生成时间轴用的同步点，含开场和循环点，不是阶段标注），没有可以通用的结构化标注。

- **算哪些敌人**：玩家打过的敌人。从玩家的技能第一次落到它身上起算；它在那之前已经变为可选（`34` 行）的，从变为可选的那一刻起算（xivanalysis 的 FIRST_TARGETED 和 TARGETABLE：可选状态的变化可以在第一次被打到之前就结束停手时间）。之后可选与否按它的 `34` 行，死亡（`25`）或移除（`04`）后算不可选
  - **只算这一场里玩家打过的**：xivanalysis 算所有敌方单位，靠的是 FFLogs 的敌我划分；ACT 日志没有敌我标记（LogGuide 的 `03` 行没有；OverlayPlugin 在 `261` 行定义了 `MonsterType`（0 友方、4 敌对），33 份国服样本里一次也没写出）。不加这个限定时，样本里有 8 场被玩家打不到的单位（无名单位、伊弗利特之灵等）误结束了离场
  - **实时要回头改**：一个单位变为可选时还不知道玩家会不会打它。第一次打到时，才把之前的离场缩短到它变为可选的那一刻，或者整段去掉；监控窗口里这种短离场会先出现、随后收回。复盘不受影响（阶段是现算的）
- **移除后又加入**：被移除（`04`）的敌人以同一个 ID 再加入（`03`）时算新单位，重新从下一次被打到（或此后变为可选）起算。LogGuide：`04` 是单位从场景移除，`03` 是加入场景。没有先 `04` 的 `03` 照旧：LogGuide 说 `03` 也可能只是单位进入视野，样本里被打过的敌人收到 `03` 41 次，24 次之前没有 `04`（优雷卡、博兹雅、木人等野外场景）
- **离场窗口**：这些敌人全都不可选的时段；有一个可选（或有新的敌人被打到）就结束。**不设最短时长、不看 HP**：xivanalysis 和 cactbot 都不用这类阈值。原先“至少 10 秒才算转场”“boss 候选 = 最大 HP 不低于主 boss 一半”“HP 锁定（5 下、2 秒不变）”三条出自样本，已去掉
- **同一时刻的变化一起算**：刚开始就结束的离场不算；在上一段离场结束的那一刻又开始的离场，并回上一段（xivanalysis 把首尾相接的停手时间合并）。这不是时长阈值，两者的长度都是 0
- **主 boss**：玩家打过的敌人里最大 HP 最高的那个，只用来显示 HP
- **不编号**：每个副本的 P1、P2 是社区攻略的叫法，不一定和离场、可选与否的划分一致，所以不叫 P 几。窗口之间的“在场”时段和“离场”窗口都按这一场里的时间命名：`00:00–00:47`、`离场 00:47–00:52`；还没结束的写“03:40 起”。直到战斗结束都没回来的窗口是战斗的结局（击杀、团灭），不算
- **筛选只列在场时段**：复盘标题下的阶段按钮、伤害表阶段列的过滤、统计页的范围只列在场时段，不列离场窗口；勾掉任何一段时，离场窗口里的受击也隐藏（筛选显示的是勾选的在场时段）。名字是这一场的时间，换一场就清掉阶段过滤
- 效果：格莱杨拉波尔（`trial-phases` 夹具）有六段在场、五段离场（三次约 6 秒的跳开各是一段离场，转场中间小怪可打的那段是一段在场）
- **只存窗口，不存阶段**：引擎把主 boss（`Encounter.boss`）和不可选窗口（`Encounter.untargetable`）记在场次上，阶段由 `derivePhases(encounter, now)` 现算；一行属于哪个阶段按时间查（`phaseAt`），行里不存。规则改了，旧存档重算就生效（3.2）
- **局限**：换体的 boss（新的 ID、相同的最大 HP）只跟踪第一体的 HP，后面阶段的 HP 停在换体时（温达斯：第三巡行的神龙）；一次拉多个小 boss 的副本，主 boss 可能中途换人。阶段只用来分段，HP 数字仅供参考
- **已知局限：友方单位被算作敌人**（2026-10-09 查，暂不修）：玩家的技能落到非玩家单位上就算“打过”，治疗、增益、道具也算，所以被治疗或加增益的陆行鸟、宠物会被当作一直可选的敌人，它在场时 boss 离开也不算离场；最大 HP 比敌人高时还会被当成主 boss。样本里只有斗兽奇弈高段 2 场（玩家对自己的魔兽用“魔兽药粉”）少了 0.9–6.7 秒的离场，副本里没有。不能按“主人是玩家”排除：野外的“护领”怪 `03` 行的主人是玩家本人，却是攻击这名玩家的敌人
- **修正记录**（2026-10-09，用户确认）：原规则只认“第一次被打到”、移除后一直算不可选、同一时刻的变化逐行算，有三处问题
  - 朱雀镇魂战：转场里，开头打过的 4 只火焰鸟在同一毫秒各收到一对“可选 / 不可选”，切出 4 段 0 秒的在场（4 次击杀都有）
  - 永远之暗歼灭战：boss 离开时招死之手一波一波来，上一波打死、下一波已经可选但还没被打到的空档（0.5–1.5 秒）算成离场。输出越快越容易出现，同一副本几场的段因此对不上
  - boss 移除后再加入、之后没有 `34` 行：瓯博讷修道院（圣骑士阿格莉亚丝）2:23.6–3:24.3 整段算离场，其中约 52 秒正在打 boss；永远之暗一场 4:25.8 起的离场开到战斗结束，被当作结局丢掉，那 14.7 秒的离场没了，监控窗口则在最后一分多钟显示离场
  - 核对（只作验证）：33 份样本 1,577 场，79 场的离场有变化（按 0.1 秒），都是原有离场的缩短、去掉，或找回被丢掉的那段，没有别处新出现的离场；格莱杨拉波尔夹具段数不变，第四段离场的结束提前 0.1–0.6 秒

## 6. 数据模型

### 6.1 受击行与死亡行（两个窗口共用）

```ts
type Row = DamageRow | DeathRow;

interface DamageRow {
  kind: "hit" | "dot";
  id: number;                 // 场次内自增
  time: number;               // 绝对时间 ms
  offset: number;             // 距开打 ms
  seq?: string;               // 21/22 序列号，同一次 AOE 相同
  targetCount?: number;
  target: { id: string; name: string; job: number };
  source: { id: string; name: string };
  action: { id: number; name: string };   // DoT 时 id = 0
  amount: number;             // 扣盾后的实际伤害
  shieldAbsorbed?: number;    // 37 行回填的估算值
  shieldBefore?: number;      // 受击那一刻身上所有盾合计（账本的快照，和 shieldAbsorbed 一起回填）；剩余 = 打穿时 0，否则 shieldBefore − shieldAbsorbed
  fullyAbsorbed: boolean;     // 0 伤害且命中前有盾
  damageType: "physical" | "magical" | "special" | "unknown";
  attackType?: number;        // 斩 / 刺 / 打 / 射 / 魔 / 暗
  element?: number;
  result: "hit" | "block" | "parry" | "miss";
  crit: boolean;
  direct: boolean;
  invulnerable: boolean;      // 命中时身上有无敌类状态
  hpBefore: number;
  hpAfter?: number;           // 37 行回填
  maxHp: number;
  multiplier: number;         // 已知效果算出的理论倍率
  multiplierPartial: boolean; // 有数值未知的效果
  targetStatuses: StatusSnap[];
  sourceStatuses: StatusSnap[];
  fatal?: boolean;
}

interface StatusSnap {
  id: number;
  stacks: number;
  remainingMs: number;
  sourceName: string;
  category: "mitigation" | "shield" | "vulnerability" | "damageUp" | "invuln" | "other";
}

interface DeathRow {
  kind: "death";
  id: number;
  time: number;
  offset: number;
  target: { id: string; name: string; job: number };
  killerRowId?: number;       // 致命一击那条 DamageRow
  sourceName: string;         // 25 行的来源
  overkill?: number;
}
```

状态的名字、图标不存进快照，渲染时按 ID 查 `statuses.json`。

### 6.2 场次存档（IndexedDB）

数据库 `mitigation-monitoring`，两个对象仓库：`encounters` 存每场的元数据（键 `id`），`chunks` 存原始行分块（键 `[id, index]`）。分开存，战斗中每次写入只追加一块，不用重写整场。

```ts
// core/archive/types.ts
interface ArchiveMeta {
  version: number;            // ARCHIVE_VERSION = 2（2：玩家坐标、开打时仍在的状态的挂上行）
  id: string;                 // `e${start}`：开打时刻，可排序；监控窗口不问写入方就能算出
  zoneId: number;
  zoneName: string;
  start: number;
  end?: number;               // 记录中为空
  result: "wipe" | "clear" | "unknown";
  lastLineTime?: number;      // 最后写入的一行的时间：分辨“还在记录”和“悬浮窗中途关了”
  self?: { id: string; name: string };
  party: PartyMember[];       // 开打时的小队（PartyChanged，带全团标记）
  combatants: CombatantInfo[];// 开打时引擎认识的全部单位（名字、职业、owner），中途打开悬浮窗也能还原
  scope?: ScopeSnapshot;      // 显示范围：记录中每次写入时更新，脱战时冻结（5.2）
  summary: {                  // 场次列表直接用，不必解压
    durationMs: number;
    deaths: number;
    rows: number;             // 显示范围内的受击行和死亡行
  };
  chunkCount: number;
  bytes: number;              // 压缩后的大小
  pinned: boolean;            // 收藏的场次不被自动清理；归复盘窗口管（一份复盘的各场一起收藏），写入方保留存储里的值
  session?: string;           // 属于哪一份复盘：这次进入区域后第一场的 id（2026-10-08 起；更早的存档没有，各自一份）
  title?: string;             // 这一场打的是谁：主要敌人（玩家打过的最大 HP 的敌人）的名字，列表用
  source?: { kind: "networkLog"; file: string }; // 从 ACT 日志导入的（9.5），记文件名；监控窗口录的没有
}
// chunks 仓库：{ id, index, data: Blob }，data 是 gzip 后的原始行
```

**一份复盘 = 一次进入区域的全部战斗**（2026-10-08，实机反馈：24 人本的几个 boss 各成一份，查看和管理都不合逻辑）。和 ACT 一样，一次进入区域（`01` 行）到离开是一份记录：24 人本的小怪和各个 boss、迷宫的各段、在一张野外地图里打的每一波怪，都在同一份复盘里。存储仍是每场一份存档（复盘时只重算选中的那一场，和监控逐行一致的做法不变），元数据的 `session` 把它们串起来；列表、收藏、删除、保留数量都按份。写入方记着这次进入区域的第一场，换区（`01` 行）后的下一场开新的一份；悬浮窗中途重新加载过的，之后的场次会另成一份（没有可靠的依据接上）。一份复盘里正在记录的那一场被复盘窗口删掉时，下一场也另开一份

- **写入**（`core/archive/writer.ts` 的 `ArchiveWriter`）：每一行先交给写入方再交给引擎，所以开打那一行也算在开打前快照里。开打时先写入 `PrepullState` 的快照：区域、自己、小队、存活单位、仍在持续的状态（连同挂上它的那条技能行：修正字节，5.4）、每个玩家开打时所在的位置（`261` 行只记变化，合并成一条），加上最近 30 秒的原始行（开打前的减伤、盾、倒计时）。之后记录每一个相关行，脱战后再记 10 秒（迟到的死亡行、胜利 / 团灭行，5.3），然后封存。监控引擎读的就是这种裁剪后的行，存档不会少了监控用过的信息（3.2）。新的一场开打时，上一场如果还没封存就立即封存
- **压缩**（`codec.ts`）：原始行去掉行尾 16 位哈希，用 `|` 和换行拼接后 gzip（`CompressionStream`，ACT 已确认可用）。不支持时存原文，读取时按 gzip 魔数区分
- **裁剪**（`codec.ts` 的 `archivedForm`）：玩家的 `38` 行只存到护盾字段；`261` 行只存玩家 `Add` / `Change` 行里的 `PosX` / `PosY` / `PosZ`（`Add` 行没有坐标也留着，省略的是 0），其余不存。10-06 炼净之狱3 一场 5 分钟，存档 gzip 后从 220 KB 增加到 243 KB。坐标原先用来判坠落和场边即死区，2026-10-07 起死因不再用它（5.7），存档仍保留
- **重算**（`replay.ts`）：新建一个引擎，先灌入区域、`party`、`self`、`combatants`（中途打开悬浮窗时存下的场次，开头没有 `01` 行），再依次喂全部行；每个事件先交给 `ReplayDetail`、再交给引擎（5.8）。从存档记的开打时刻那一行开场（5.3），找到这一场；存档里没有那一行就报“存档里没有找到这场战斗的开始”，不拿别的场次顶替。显示范围用存档里冻结的，记录中的场次用重算出来的
- **保留策略**：每次封存后，按最近一场的开打时间保留最近 N 份复盘、删掉更早的整份（设置“保留复盘份数”，默认 20，5~100；改小后立即清理），收藏的、正在记录的、以及这次进入区域还没离开的那一份不计入、不删
- **不存档的区域**（设置，2026-10-08 起取代“不保存非副本内的战斗”的是 / 否）：树状复选框，按游戏数据列出全部区域（`core/game/zones.ts`，9.4）：
  - **副本**：按游戏自己的内容类型（ContentFinderCondition → ContentType）分为迷宫挑战、讨伐歼灭战、大型任务、绝境战、诛灭战、特殊迷宫探索，超过 10 个的再按版本（ExVersion）分，最下面是每个副本
  - **野外地图**：TerritoryIntendedUse 1（Overworld），按版本分
  - **特殊场景**：其他内容类型（禁地优雷卡、天佑女王、新月岛、深层迷宫、寻宝、对战、行会令、任务战斗……）；不是副本的区域（任务场景、单人任务、季节活动等）合成“其他区域”一项，不逐个列出
  - **不会有战斗的地方不列出**（2026-10-08）：按 TerritoryIntendedUse 整类去掉名字上就明确不是战斗场所的：主城 0、旅馆 2、GM 牢狱 5、等候区 12、房屋 13 / 14、陆行鸟赛跑 20、天穹街 21、十二神大圣堂（婚礼）22、金碟游乐场 23、萌宠之王 25、军营 30、九宫幻卡 35 / 50 / 51、虚景跳跳乐 44、出海垂钓 46、无名岛 49、金碟巨豆中心 59、宇宙探索 60；再按内容类型去掉采集、制作的副本：16 大地使者（出海垂钓、天上福地云冠群岛）、17 能工巧匠。这些区域不在树里，也从不存档（`isNoCombatZone`）。名字看不出有没有战斗的（单人任务场景、季节活动等）留在树里
  - TerritoryIntendedUse 的取值含义按 FFXIVClientStructs 的 `TerritoryIntendedUse` 枚举（游戏数据里这张表没有名字）
  - 勾选的区域里开打的战斗不建存档（`ArchiveWriter` 的 `accept`），监控窗口照常显示并在工具栏标“不存档”。勾一个分类就是这个分类下的全部，以后游戏更新加进这个分类的副本也算；分类下只勾了一部分时显示半选；取消勾选一个通过上层分类勾上的副本，等于勾上这个分类里的其他各项。设置里存的是勾选的节点（`skipZones`，`core/settings/zoneSkip.ts`），游戏数据里还没有的新区域不属于任何节点，照常存档（可能是新副本）。默认勾选野外地图和特殊场景，即只存副本；设置里的“恢复默认”回到这个状态，旁边的“全部清除”是全部存档。之前版本存下的设置（只有“不保存非副本内的战斗”的是 / 否）读取时一律换成这个默认
  - 有搜索框，按名字找副本或地图，显示命中的项和它上面的分类
- **解除限制进入的副本不自动存档**（设置，2026-10-09，默认开）：
  - 来源：OverlayPlugin 每次换区写一条 `265` 行（ContentFinderSettings，LogGuide），字段是区域 ID（十六进制）、区域名、这个区域有没有副本设置、然后是各项设置，`1` 为开：`265|时间|区域ID|区域名|有无设置|解除限制|最低品级|超越之力无效|自由探索|等级同步`，解除限制即 `unrestrictedParty`。OverlayPlugin 源码（`LineContentFinderSettings.cs`）在换区时写，ACT 启动后的第一行日志时也补写一条当前区域的
  - 读的是这次进本时生效的设置，不是自己副本设置窗口里的勾选：OverlayPlugin 7.1 读 `ContentsFinder` 偏移 0xA8 起的 5 个字节，按“解除限制、最低品级、等级同步、超越之力无效、自由探索”的顺序取，对得上 FFXIVClientStructs 的 `ContentsFinderQueueInfo`（`ContentsFinder` + 0x20）里 0x88 起的 `PoppedContentIsUnrestrictedParty / IsMinimalIL / IsLevelSync / IsSilenceEcho / IsExplorerMode`；所以小队成员看到的也是队长进本时的设置
  - 引擎记住最后一条 `265` 行；开打时它说的区域就是当前区域、且解除限制，这一场标上 `unrestricted`（`Encounter`）。`265` 和 `01` 都是换区时写，谁先谁后不一定，所以按区域 ID 对，不按先后
  - 设置开着时，这样的场次不建存档（`archivesEncounter`，和“不存档的区域”一起在 `ArchiveWriter` 的 `accept` 里判断），监控窗口照常显示并标“不存档”，悬停说明的原因里有解除限制。工具栏不另加“解限”标签（2026-10-09 决定：475px 宽时零式这类长副本名已经被截断，再加一个标签会挤掉“中量级2”这样的后半截）。只管监控窗口的自动存档：复盘窗口导入 ACT 日志（9.5）不看这个设置，解除限制的日志照常列出场次、导入、解析（`logImport.test.ts`）
  - 认不出时照常存档：进本之后才打开悬浮窗（`265` 已经写过，后订阅的页面收不到）；OverlayPlugin 找不到这块内存（游戏更新后签名失效）时不写 `265`
  - 国服日志里有没有 `265` 行、值对不对，还没有核对（测试夹具只留引擎读的行，看不出）
- **两个窗口共用存储**：监控窗口写正在记录的场次，复盘窗口收藏、删除、更正摘要。元数据的“读-改-写”一律走 `ArchiveStore.update`：在同一个 IndexedDB 事务里读出、改好、写回，另一个窗口的写入插不进中间
  - **收藏**：复盘窗口用 `update` 只翻转 `pinned`，一份复盘的各场一起翻；写入方每次写元数据也用 `update`，保留存储里的 `pinned`；已收藏的一份里新开的一场也是收藏的
  - **删除正在记录的场次**：写入方下一次写入时发现元数据没了，就删掉刚追加的那块、停止记录这一场，监控窗口工具栏标“不存档”。不会再出现“删了又冒出来、缺了开头”的残缺存档
  - **旧存档的摘要**：场次列表里的行数、死亡数是记录时算的。复盘窗口打开一场时会按当前代码重算，不一致就写回（修复野外战斗之前存的场次会从“0 行”变成实际行数）；写回前确认这期间写入方没有再追加内容，否则以写入方的为准
- **悬浮窗中途关掉的场次**：没有 `end`，原先会一直显示“记录中”、也永远不会被清理。监控窗口启动时、以及每一场新开打时（`ArchiveWriter.closeAbandoned`）把超过 1 分钟没有写入的“记录中”场次结束掉，以最后写入的一行的时间作为结束时间，结果记为未知
- **写入失败的块**（存储满）：后面的块照常写，复盘打开时块数少于 `chunkCount` 就提示“这场存档缺少 N 段数据”
- **打开数据库**：失败的下次重试；被另一个页面的旧版本挡住（blocked）时等它关掉，不算失败；别处打开了新版本时关掉这个连接，下次重新打开
- **导出**：单场或多场打包成一个 `.json.gz` 文件；导入同样格式（M9）
- 存档的来源是可替换的，以后导入 ACT 网络日志文件也落成同样的存档（9.5）

### 6.3 复盘模型（打开存档时生成，不存储）

```ts
// core/archive/replay.ts：replayArchive(meta, lines) 的结果
interface ReplayResult {
  engine: Engine;                  // 重算用的引擎
  encounter: Encounter | undefined; // rows：受击行、死亡行（6.1）；boss、untargetable：主 boss 和不可选窗口（5.9）
  visible: ScopePredicate;         // 存档冻结的显示范围
  detail: ReplayDetail;            // 5.8
}

// core/replay/detail.ts
class ReplayDetail {
  heals: HealEvent[];              // { kind: "heal" | "hot", time, target, source, action, amount, hpBefore, maxHp, overheal }
  statusChanges: StatusChange[];   // { time, target, status, stacks, source, change: "gain" | "refresh" | "lose", durationMs, category }
  casts: EnemyCast[];              // { time, source, action, target, castMs, cancelled? }
  hpOf(playerId): HpPoint[];       // { time, hp, maxHp, shieldPercent }
}
```

在这之上按需计算，都是纯函数：`derivePhases` / `phaseAt`（阶段，`core/engine/phases.ts`，监控窗口也用），以及 `core/replay/` 下的 `buildDeathReplay`（某次死亡的时间窗：事件、HP 曲线、致命一击或其他死因、合计）、`aoeGroups` / `missingMitigation`（AOE 对比）、`memberStats` / `abilityStats`（统计），M8 加 `buildTimeline`（时间轴的泳道模型，含状态区间，8.6），M8.4 加 `buildPartySkills` / `partySkillsAt`（队伍减伤技能，8.2）。

  - **冷却**：从这一刻之前队员的技能使用（5.8）推算：每用一次扣一次积蓄，过一个复唱时间回来一次；共用复唱组的一起算（原初的血气和原初的勇猛）；以为没有次数时又用了（上一次在存档开始之前），从这次重新算。团灭和换区时全部转好；个人死亡不重置（游戏里冷却只在团灭时重置，Square Enix 官方论坛的玩家讨论；Skills Monitoring 也只在团灭、换区时重置）
  - **盾被打破时缩短复唱**（2026-10-09，用户确认）：技能说明写“（附加自身的）防护罩因吸收到足够的伤害而消失时，X的复唱时间缩短N秒”的（坦培拉涂层 60 秒、油性坦培拉涂层 30 秒，都缩短坦培拉涂层；9.4），这层盾被打破时 X 的剩余复唱减 N 秒（没在冷却就不减）。哪层盾：队员自己最近一次施放这个技能给自己挂上的那个状态（施放行的 `0x0E/0x0F`）。打破：盾提前消失，并且护盾计算（5.6）认为它被受击用掉了——被打穿的一下用完，或消失时正有受击在结算（含 DoT 跳伤），或消失在一条护盾报告的同一刻；到期消失、消失时没有受击的不算（`ShieldAccount.shieldLost` 的返回值，复盘记在 `ReplayDetail.shieldsUsedUp`）。被解除不算：同一时刻队员施放了说明里写“解除自身附加的S”的技能（油性坦培拉涂层），并且它真的挂上了状态。按了油性却什么都没挂上的（坦培拉涂层先被打破了，前提状态没了），坦培拉涂层照常算打破
    - 依据：技能说明（游戏数据）；游戏数据里没有别的字段标这个效果，服务器只把复唱变化发给本人的客户端，日志里没有别人的复唱。说明的措辞变了导入会停下（9.4），不会悄悄丢掉
    - 样本核对（29 份非空日志，只核对，未据此定规则）：画家自己身上的坦培拉盾 119 层，到时消失 29、被油性解除 28、提前消失 60；60 次提前消失每次当时都有伤害打在他身上（47 次结算行同一毫秒，11 次早 2–9 毫秒，2 次是 DoT 跳伤），没有一次是机制清盾。用 94 次坦培拉涂层核对“用的时候模型是否显示可用”：不减复唱有 12 次显示冷却中，按本规则减（共 60 次）一次都没有
    - 仍可能错：副本机制清掉盾、或非伤害致死，恰好和一下伤害结算在同一刻，会被当成打破多减一次（日志的 `30` 行不写消失原因）；样本里没有出现
  - **生效中**：同时间轴的施放段（8.6）：从施放开始，按这次施放挂上的状态的持续时间，盾被打破、人走出圈都不缩短。段的施放是队员本人的技能，就按技能对上；召唤物施放的、没有施放行的（光环补发），归到 1.5 秒内刚用过的减伤技能，优先说明里写了这个状态的那个
  - **日志里没有的**：开打 30 秒以前用过、开打时效果已经结束的技能存档里没有（6.2 只留开打前 30 秒的行和仍在身上的状态），显示为可用；忠义、蛇胆、以太超流、魔力和小仙女是否在场日志里没有，“可用”只表示复唱转好了。来源和误差写在计算说明里（8.1）
  - 实现：`core/game/defensives.ts`（某职业某等级有哪些减伤技能），`core/replay/partySkills.ts`（`buildPartySkills` 按队员整理使用和生效段，`partySkillsAt` 给出某一刻的状态），`app/components/review/PartySkills.vue`、`SkillIcon.vue`。复盘页按打开的场次算一次，选中行时才算

### 8.3 死亡回放

左边是本场死亡列表（时间、职业、名字、阶段、死因：致命技能、地形杀、即死、标注的机制，或“{凶手}（无伤害记录）”），摘要的死亡句子后面也注明阶段。监控窗口死亡行的 `↗` 直接打开这次死亡的回放。选中一次死亡后：

- **摘要**：死亡句子、溢出量；致命一击的技能、来源、伤害（占最大 HP）、受击前 HP、盾吸收、减伤率和当时的状态图标；没有致命一击时写死因（地形杀、即死、标注的机制）或“没有伤害记录”和 `25` 行的击倒者（5.7）；最后几秒的合计：受击次数和伤害、盾吸收、治疗次数、有效治疗、溢出
- **时长**：10 / 15 / 20 / 30 秒，默认 15 秒，记在 `mitigation-monitoring:death-window`
- **HP / 护盾曲线**（`HpChart.vue`，SVG）：HP 是阶梯面积，护盾叠在上面，横线是最大 HP 的 25% 刻度，红色竖虚线是死亡时刻。下面一条标记带：受击向下（红），治疗向上（绿，浅色部分是溢出），高度按占最大 HP 的比例；敌方读条是顶上的橙色三角。鼠标停在图上显示那一刻的 HP 和盾；点标记选中对应事件
- **事件列表**（新的在上）：距死亡秒数（悬停看战斗时间）、类型、内容、数值、备注、减伤率、之后 HP（条和百分比）。类型有受击 / 致命 / 持续伤害、治疗 / 持续治疗、获得 / 刷新 / 层数 / 未生效 / 失去（状态，含义见 5.4）、读条、死亡。点受击行打开详情侧栏
- **显示开关**（记在 `mitigation-monitoring:death-show`）：受击、治疗、状态、含无关状态（默认关，进食、姿态这类）、敌方读条（老存档没有读条记录时灰着）
- **归并**：死亡那一刻（150 毫秒内）失去的状态合成一行“随死亡失去 N 个状态”；同名单位 1 秒内开始的同一个读条（Boss 的分身、一排小怪）合成一行“×N”

### 8.4 AOE 对比

- 上半部分：本场所有命中 ≥ 4 个显示范围内玩家的伤害（同序列号），列出时间、阶段（多于一个阶段时）、技能、来源、人数、平均 / 最低 / 最高伤害、平均减伤、死亡数；可按技能筛选，按时间 / 最高伤害 / 平均伤害 / 死亡排序
- 下半部分：选中那次的每个人，伤害（带同组相对长度的底条）、占最大 HP、**盾量**（受击那一刻身上所有盾合计，悬停看盾吸收）、**剩余**（这一下之后剩下的盾，打穿时为 0）、**穿盾**（有盾时落到 HP 上的伤害，没打穿写“未穿”，身上没盾写“无盾”）、减伤率、未减伤估算、之后 HP、状态图标、**缺少**、判定；点一行打开详情
- **用途**（2026-10-07 需求）：复盘时看这一下打上去，各人身上叠的盾还剩多少、有没有打穿、打穿了多少，用来决定下次编排盾技能时要加盾还是可以减盾。穿盾量就是日志里这一下的伤害，没有误差；盾量和剩余由护盾报告推算，精度同盾吸收（日志的护盾比例只到最大 HP 的 1%，向下取整，剩余显示的是下限）。不按层给数：日志里没有每层盾各自的量
- **缺少**（`missingMitigation`）：同一次伤害里，超过半数的其他人身上有、这个人没有的减伤和盾。团减没覆盖到、盾没给到的人一眼可见；个人减伤只在一个人身上，永远不会被算作“缺少”

### 8.5 统计

- **按队员**：受击次数、承伤合计（带底条）、占全队、其中 DoT、盾吸收、平均减伤、最大一击、死亡
- **按伤害名称**（按名字 + 来源分组）：施放次数（不同的序列号，DoT 每跳一次）、命中、合计、平均、最高、平均减伤、致死次数
- **统计范围**：多于一个阶段时可以选“整场”或某一个阶段，两张表都只算这个阶段
- 点名字跳到受伤明细，只看这个人 / 这个技能（清空复盘窗口的其他过滤条件；选了阶段时连阶段一起带过去）
- 原计划“按成员拆分伤害名称”没做：受伤明细里只看一个人再按伤害名称过滤，效果一样

    - **段长**：取技能行给施放者挂上的状态的时长，排除游戏数据里作为别的技能使用条件的状态（Action 表的 `ActionProcStatus`：节制同时给的“神爱抚预备”是神爱抚的使用条件）。剩下**恰好一个**才用它；零个或多个时不猜，这一段只画施放那一刻，悬停写“持续时间未知”（`lengthUnknown`）。不用命名或时长去挑：命名可能变，也可能有两个时长一样的状态
    - 补发和之后走进范围的人并进正在持续的那一段，不另起一段、也不延长
    - 队员身上的减伤在游戏数据里是常驻状态（5.4），自身没有时长；对不上施放时（开打前挂上的）按它实际消失的时刻
    - 修正记录：M8 原来按“施放者身上同名的标记状态”配对、段长取标记和状态自身时长中较长的；10-07 改常驻状态的列号后，常驻状态按无限算，段一直画到场次结束（实机反馈：节制画满全场），2026-10-08 改为上面的规则。核对：歼灭战夹具的节制 20 秒，24 人夹具的野战治疗阵两次各 15 秒。那次节制的队员减伤只补发到第 12 秒：boss 的“无尽狂奔”转场，整队被抬起后换到另一块场地，期间不再补发；施放者的 1872 照常满 20 秒
  - **再次施放**：同一个人在前一段还没结束时又给同一个目标施放（残暴弹、连续两次均衡预后），前一段截止在新施放的时刻。同时给不同的人的（两层充能的神祝祷、天星交错，或者刚玉之心顺带给队友挂的残暴弹）在这一行里分上下两条，所以永远不重叠，行高随之增加
  - **没有施放可对应时**（开打前就挂上、存档里没有那条技能行）：从获得时刻开始，按状态的时长
  - 实测：格莱杨拉波尔夹具里节制 20 秒 ×8、摆脱 30 秒 ×8；样本里野战治疗阵每次 15 秒 ×8、均衡预后连续施放首尾相接
- **召唤物算主人**：小仙女、炽天使等的施放归到主人的组里
- 只显示显示范围内的队员（5.2）。8 人默认全部展开；24 人默认只展开自己的小队，其余只留组标题行

**看减伤安排的交互**

- **固定在上方**：阶段、Boss 读条、Boss 增伤、团队受伤、自动攻击这几行在上下滚动时固定不动，往下看队员的减伤时始终能对照 boss 技能和伤害（实机反馈）
- **好选中**：竖条再细，鼠标在它左右约 9 像素、整行高度内都能选中；队员 HP 里的受击刻度同理（7 像素）
- **悬停在团队受伤竖条上**：一条竖线贯穿所有泳道，当时生效的状态条保持高亮、其余变暗，一眼看出这一下被哪些减伤覆盖；提示里写技能、来源、命中人数、合计、平均减伤、死亡，以及“缺少”：多数人有、某些人没有的减伤和盾（`missingMitigation`，8.4）
- **悬停在状态条上**：状态名、施放者、对象（×8 时列出谁）、没挂上的人（“未覆盖：某某（身上已有更强的同类效果）”）、持续时间、这段时间里落下了哪几次伤害；灰色图标（一个人都没挂上）悬停写谁没挂上
- **点击**：受伤竖条打开这次伤害里伤害最高的那一行的详情侧栏（8.1 共用，侧栏里有同一次施放命中的所有人）；受击刻度打开那一行；死亡切到死亡回放的这次死亡；阶段色块缩放到这个阶段。地址里的 `row` 同受伤明细，切到时间轴时滚动到它并高亮
- 鼠标所在的时刻显示在竖线顶上：战斗时间加这一段内的时间，如“04:22 · 在场 +00:12”（离场之后的机制从这一段开始起算，5.9）

**缩放与平移**

- 横轴是战斗时间（`mm:ss`，开打前为负），刻度间隔随缩放在 1 / 2 / 5 / 10 / 15 / 30 / 60 秒里选，相邻刻度至少隔 60px
- 打开时显示开头约 2 分钟（比这短的战斗显示整场）。最多放大到 80 px/秒；最多缩小到整场刚好放进窗口，不能再小，到头时 `[−]` 灰掉。“适应全场”就是缩到最小。不记住上次的缩放，每场都从 2 分钟开始
- 缩放：Ctrl+滚轮（以鼠标所在时刻为中心）、触摸板双指、`[−] [+]`
- 平移：按住拖动；Shift+滚轮或触摸板横向滑动。普通滚轮保留为上下滚动泳道：8 个人展开后泳道比一屏高，这一点和示意图的“滚轮平移”不同
- 折叠状态记在 `mitigation-monitoring:timeline-collapsed`。记录中的场次随存档重载更新；视口右边缘贴着场次末尾时，跟着往后走

**实现**

- **数据**：`core/replay/timeline.ts`，纯函数，只管时间不管像素。`timelinePlayers(rows, party)` 定出显示的队员和顺序（坦克、治疗、输出，同一职能按小队列表的顺序；小队数据来自 `11` 行时只有 ID，名字和职业要等 `03` 行，缺的用这个人的受击记录补上）；`buildTimeline({ start, end, rows, detail, phases, players })` 生成泳道模型：按施放生成的段（`castSpans`）、召唤物归主人、每种状态一行（时间上重叠的段分上下几条）、读条合并和分行（按开始时间放进第一条放得下的行）、受伤竖条。单测用合成数据测各条规则，再用 hunt 夹具整体核对
- **补一项数据**：`ReplayDetail.enemyStatusChanges` 收敌人身上按施放方分类有意义的状态：队员挂的减益（`statusCategory(id, "source") === "damageDown"`）和敌人自己的增伤（`damageUp`），规则同队员身上的（5.8）。单独存放，死亡回放只看队员身上的，不受影响。状态的来源是召唤物时记下主人（`source.ownerId`，从 `03` 行的归属得来）。另收 `playerCasts`：队员（含召唤物）挂了状态的施放，见 5.8 的表
- **画图**：`app/components/review/timeline/`：`TimelineView.vue` 管视口、泳道列表、刻度、悬停竖线、提示框和缩放平移；`TlPhases`、`TlCasts`、`TlDamage`、`TlSpans`、`TlHp` 各画一种泳道；`hover.ts` 把鼠标所在的东西变成提示文字。图标、文字条和色带用绝对定位的 HTML（文字截断、缺图标时的占位都现成），HP 曲线用 SVG。视口换算、刻度、可见判断、曲线降采样在 `app/timelineView.ts`（纯函数，单测）。不引入图表库
- **性能**：左边泳道名一列固定，右边所有泳道共用一个横向视口，只画和可见时间范围相交的元素，HP 曲线按像素降采样（每个像素列保留最低、最高和最后的值）。量级：8 人 7 分钟约 750 条受击、几百段状态、每人几千个 HP 点；24 人约 3 倍，裁剪后每次只画几百个元素

**原型之后**

- **减伤技能的冷却**：只做上面这些减伤、盾、减益对应的技能，不做全部技能。在施放段后面用更浅的颜色画到冷却结束，看出某次伤害时哪些减伤“当时转好了却没用”。数据和某一刻的状态已经有了（M8.4：`defensives.json`、`core/replay/partySkills.ts`，详情侧栏在用，8.2），泳道里还没画。原计划复用 Skills Monitoring 的 `actions.json`，改为本项目自己从国服数据导入（9.4）
- **多场对比**：同一副本的几次挑战按阶段开始对齐，比较 boss 技能时间和减伤安排的差异

**参照：cactbot 的时间轴怎么来的**（2026-10-05 读 OverlayPlugin/cactbot `d8b89c1`）

- 时间是作者从自己的 ACT 日志里取、再人工调整的：`make_timeline.ts` 取一次战斗里来源是敌人的 `21/22` 行，以 `260` 进入战斗（或区域封锁消息）为 0 秒，相邻间隔累加，精确到 0.1 秒；后续阶段由作者用 `-p 技能:时间` 放到 500、1000 这类远处的时间；`test_timeline.ts` 拿别的日志检查每个同步点的偏差（0.3 秒以内为好）
- 运行时每个同步点有个窗口（默认前后 2.5 秒），窗口里看到匹配的日志行就把当前时间校准过去；阶段之间靠很大的窗口（如 `window 400,0`）跳转，所以它也不区分时间轴和血量轴
- 431 个副本的触发器里 310 个有时间轴
- 对本项目：存档里已经有它需要的全部数据（敌方 `21/22`、`34`），还多了 `20` 读条；阶段（5.9）相当于作者手工做的 `-p` 和 `-it`。所以泳道图直接画这一场实际发生的事，不依赖 cactbot 的时间轴文件

## 9. 技术方案与工程结构

### 9.1 技术栈

沿用 Skills Monitoring：**Vue 3 + Vite + TypeScript + vitest + pnpm**，构建成单文件 IIFE（`file://` 下 CEF 不加载 ES module），图标随包发布，运行时不联网。两个窗口是同一个产物的两个路由（`#/` 监控、`#/review` 复盘、`#/settings` 设置）。

- 表格：不引入 AG Grid 这类重型表格库（体积约 1MB，样式覆盖麻烦）。手写表格 + `@tanstack/vue-virtual` 虚拟滚动
- 图表：复盘的 HP 曲线和时间轴用 SVG 手绘，数据量不大，不引入图表库
- 存储：IndexedDB 用薄封装（如 `idb`，约 1KB），或直接手写

### 9.4 游戏数据与图标

- **导入脚本** `pnpm import-data`（`scripts/import-game-data.ts`）：从 thewakingsands/ffxiv-datamining-cn（国服客户端导出）按 git 提交锁定版本下载 CSV，缓存在 `node_modules/.cache/game-data/`，生成 `src/data/generated/` 下的文件并提交到仓库。当前锁定 `9ac8b57b`（ver 2026.09.15，与 Skills Monitoring 相同）
- **普通攻击表** `autoAttacks.json`：Action 表里 ActionCategory = 1 的技能 ID，1,533 个，9 KB

### 9.5 导入 ACT 网络日志（M8.5）

2026-10-08 实现（需求：可以选择日志里的某个场次转为可复盘的记录）。复盘窗口左栏标题栏的“导入”打开导入面板：

1. **选文件**：按钮打开文件选择框（`.log`），或把文件拖进面板。提示 ACT 默认的日志目录 `%APPDATA%\Advanced Combat Tracker\FFXIVLogs\`
2. **扫描**：读一遍文件，列出其中所有场次，按“一次进入区域”分组（同 6.2 的一份复盘），每场写开始时间、主要敌人、过本 / 团灭、时长、死亡数、受击条数；文件在战斗中结束的写“日志在战斗中结束”。有进度条，可取消
3. **勾选**：单场勾选，或勾组标题选这次进本的全部。已经在复盘列表里的场次（监控窗口录过，或导入过）灰掉不可选，标“已在复盘里”
4. **导入**：再读一遍文件，把选中的场次写进存档，完成后关闭面板、刷新列表、打开第一场。可取消，已经写完的场次保留

**和监控窗口完全同一条路径**：导入用的是同一个引擎和同一个存档写入器（`ArchiveWriter`），只是喂的是文件里的行而不是 OverlayPlugin 的 `LogLine`，喂的顺序也相同（先写入器、后引擎，`useLiveEngine`）。所以场次怎么切、开打前的状态快照（6.2）、存档格式都和实时录的一样，复盘重算出的每一行也一样（`tests/logImport.test.ts`：导入的存档重算结果与引擎直接跑日志逐行相同）。存档 ID 由开打时间定（`e<毫秒>`），同一场在监控录的和导入的 ID 相同，靠它认出“已导入”

**日志文件和实时的差别**：文件里没有 `PartyChanged` 和 `CombatData`。小队取 `11` 行（只有 ID），名字、职业、等级取 `03` 行；`11` 行常常早于成员的 `03` 行，所以引擎收到小队成员的 `03` 行时补上缺的名字、职业、等级（`PartyState.fill`，实时模式同样受益，`PartyChanged` 给过的不改）。自己取 `02` 行。显示范围退回为小队成员（5.2）：24 人副本只显示自己的小队

**导入的存档**：
- **自动收藏**：导入的场次日期往往比现有的早，不收藏的话下一次按保留份数清理（6.2）就会先删掉它们。面板里写明“导入的复盘自动收藏（★），不会被按保留份数清理”；取消收藏后照常清理
- **归哪一份复盘**：扫描时按日志里的进本分组，一份复盘以这次进本的第一场命名（`session`），和监控窗口一样。只导入其中几场时也用这个名字，所以导入的场次能和监控窗口录过的同一次进本的场次合成一份
- **导入不清理别的存档**，也不去结束别的“记录中”的存档（写入器的 `imported` 选项）；记下来源文件（`source`）

**读文件**（`core/archive/logFile.ts`）：按 4 MB 分片读（`Blob.slice`），跨分片按 UTF-8 解码，按行切开（兼容 CRLF），每行按 `|` 切成数组；行尾的 hash 由存档编码去掉（`withoutHash`）。从不整个读进内存。在复盘窗口的主线程上跑，每个分片之间让出，界面不卡：用夹具拼成的 124 MB 合成日志（全是战斗行，比真实日志密）在 Node 里扫描 2.6 秒、找出 80 场，导入最后一场 3.1 秒，每个分片最长占用 0.12 秒。原计划的 Web Worker 没用：`file://` 下 Worker 受限，量级上也不需要

**实现**：`core/archive/logImport.ts`（`scanLog` 列出场次，`importLog` 导入选中的场次，输入都是“每次重新读一遍的分批日志行”，与界面无关，可单测），`core/archive/logFile.ts`（Blob 分片读成分批的行），`app/components/review/LogImport.vue`（面板）。原计划的 `ArchiveSource` 接口没有单独做：导入只是换了喂行的来源，写入器本身就是那个接口

**以后**：导入 / 导出存档文件（M9）；导入时选择显示范围（全团）——日志里分不出其他小队，要看 ACT 实机的 `11` 行和 `PartyChanged` 能给出什么

- **护盾吸收**（`tests/shield.test.ts`、`tests/parse.test.ts`）：快照模型：打进了伤害的一下拿走受击行那一刻的盾、吃不到之后挂上的；另一下自己的 `37` 显示在它之前快照的扣减；按种类先后扣（神爱抚先于鼓舞、激励先于鼓舞）；上盾行的最低字节定盾量；盾量按技能说明的比例 × 施放者等级（均衡预后 80 级 230%、90 级 320%）；伤害为 0、没有 `37` 的受击按护盾判断打没打到（护盾显示被吃掉的打到了，护盾没动、伤害已知的没打到）。以下是此前的用例，按新模型保留：单下全吸收由前后报告定；精简的 `37` 行不算报告，这一下自己的是精简行时在下一次报告结算；打穿的拿走全部；同段几下按预期伤害和不确定度分；按自己的 `37` 归段，不按同序列号别人的；没有自己 `37` 的按报告和延迟落段；泛输血补层（有 `26` 和只在 `37` 状态字段里两种）；`38` 行作报告，同一时刻先到的 `37` 不算；神爱抚被移除时滞后的 `38`；两层盾破一层，另一层还在；多段伤害同一序列号的几行都生效；没有报告收尾时按估计；过期没有 `30` 的盾不再吸收；伤害 0 而盾没少的不算全吸收；闪避、无敌、没盾的都是 0；没有自己 `37`、盾也没变的判为没生效（吸收 0、HP 不变、伤害不计入）；同一毫秒排在受击行后面的报告可以显示它；没有自己 `37` 的按血量判断打没打到；0.3 秒后的快速补层也能认出；挪到同一处的几下保持原来的先后；“提前显示”等下一条报告到了再决定；多段伤害几行都有受击后 HP；致命一击优先取结果行已到的；生效时刻不确定的几下一起决定（一下提前显示、一下没有结果行）；治疗重新施放的盾不按上一层估计。解析：`37` 状态字段、`38` 行。统计（`tests/replay.test.ts`）：没生效的受击不计入合计
- **护盾吸收的整体验证**（不进单测，5.6“检验”）：把全部样本日志逐份切成存档、逐场 `replayArchive`，新旧两本账并排比：快照真值、同施放参照、报告单独定准的段（按实测可见规则）、同一人连续吃同一技能的一致性。`scripts/validate-shields.ts` 按旧口径（只认受击自己的 `37`）逐段对账，仍可用，但它会把扣减划到错的段上
- **易伤与副本减伤的日志数值**（`tests/effect.test.ts`、`tests/statusTracker.test.ts`、`tests/multiplier.test.ts`、`tests/format.test.ts`）：挂状态效果的两个修正字节按有符号读、`0E` / `0F` 分目标和来源；状态带上挂它那一行的字节（行在前、在后都行，重发保留，3 秒外不认）；易伤 = 字节 × 层数，同一状态不同值；只限物理 / 魔法的对另一种为 0、对吐息未知；副本减伤取负字节；技能说明的数值优先于字节；没有字节或符号不对时未知；未减伤估算除掉已知的易伤，含数值未知的易伤时标 `≤`
- **状态说明的分析**（`tests/statusEffects.test.ts`）：作用范围只看自己那一小句（物理 / 魔法 / 元素）；条件性的（锁链、距离、方向、特定攻击、光暗属性）记为条件；多种增减效果时按符号取字节或不取；保底 1 血显示为无敌类但不让伤害无效；“移动到不会受到伤害的安全位置”不是无敌
- **死亡**（`tests/death.test.ts`）：`25` 行没有凶手、没有一下的 `37` 显示归 0 的是地形杀，不挂在之前那一下上（`37` 显示有血的一下、没有 `37` 的一下都一样）；没有凶手时 `37` 显示归 0 的一下是致命一击；cactbot 标注的击退至墙是地形杀（凶手有名字也是），之后有伤害就不算，其他副本不算；标注的机制（没解死宣）按原文显示；有凶手时取最后一下生效的受击；有凶手却没有伤害记录的写明击倒者；别人同时死不影响；同一时刻几下显示 0 取第一下；即死效果是死因；HP 归 0 的时刻不被死后的 0 覆盖；下一场开打后才到的死亡行归 HP 归 0 的那一场；存档只留玩家的坐标
- **判定**（`tests/format.test.ts`）：格挡、招架和全吸收同时标出，未生效、无敌单独标
- 承伤系数的测试随功能去掉（2026-10-07）
- **减伤数值的生成**（`tests/gameDataMitigation.test.ts`）：说明按职业、等级渲染；一种数值和分物理魔法、“会减轻”、全角数字；各状态的段落、不带名字的追加效果、技能名不是状态名时；“无法……共存”分组；生成表里盾阵、原初的武猛、策动、同组、昏乱的数值，原初的勇猛没有。盾量（同一文件）：按状态名、按“技能名效果量”、技能自己的盾；按层数的几档、摆脱每解除一个状态加 2%；生成表按施放者等级取值，由别的技能变出来的技能（均衡诊断）按 ClassJobCategory 的职业渲染
- **减伤倍率**（`tests/multiplier.test.ts`）：目标减伤与来源减益相乘；按伤害类型取值（吐息、无攻击类型只吃不分类型的）；同组不叠加只算最强；易伤增伤不计入；数值未知标 `?`；按等级、按施放者取值；格挡、招架按伤害效果写的减免，没写时未知；防护职业被动不计入
- **持续伤害的来源**（`tests/dot.test.ts`）：目标身上只有一种持续掉血的敌方减益时用它的名字和施加者，同名的几个算一种，两种不同的或没有时是“持续伤害”；hunt 夹具的跳伤全部认作“护龙威压”。常驻（`tests/statusTracker.test.ts`）：关心写 60 秒也按常驻；歌每 3 秒重发，按游戏数据常驻到 `30` 行，重发不算重新挂上；吸收时重发的盾按剩余时间

### 9.7 存储命名

- `localStorage` 键统一以 `mitigation-monitoring:` 开头（同 Skills Monitoring 的做法）
- IndexedDB 数据库名 `mitigation-monitoring`，BroadcastChannel 名 `mitigation-monitoring:live`

### 9.8 发布

沿用 Skills Monitoring 的流程（它的 DESIGN.md 第 14 节）：图标不进 git，GitHub Actions 访问不到本机解包目录，所以在本机打包，上传为 Release 附件，Actions 负责部署到 Pages。

```
本机 pnpm release
  ├─ 1. copy-icons     从解包目录复制图标到 public/icons/
  ├─ 2. test + build   运行测试，vite build 输出 dist/（包含图标）
  ├─ 3. 打包           dist/ → release/mitigation-monitoring-vX.Y.Z.zip
  └─ 4. 上传           创建 GitHub Release vX.Y.Z（先建草稿、传完附件再发布）

GitHub Actions（Release 发布时触发，.github/workflows/deploy.yml）
  └─ 下载附件 → upload-pages-artifact → deploy-pages
```

- 源码仓库 [garfieldzasv/Mitigation-Monitoring](https://github.com/garfieldzasv/Mitigation-Monitoring) 是公开的，Pages 直接从这个仓库部署，站点是 <https://garfieldzasv.github.io/Mitigation-Monitoring/>（同 Skills Monitoring）

- 一份产物同时用于在线地址和本地文件（IIFE 单文件，`base: "./"`，hash 路由）
- 悬浮窗网址填站点根地址；复盘窗口是 `.../#/review`，设置页是 `.../#/settings`

- 仓库一次性设置：Pages 来源选 GitHub Actions；`github-pages` 环境的部署规则加上标签 `v*`
